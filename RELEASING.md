# Выпуск релизов

Правила выпуска «Волны»: версия, тег, changelog, артефакты и каналы доставки.
Это политика, а не инструкция по инструменту: механизм описан в §10 и может смениться,
не меняя правил.

**Нормативные документы.** Версии зафиксированы, чтобы «semantic versioning» не означал
у разных участников разное.

| Документ | Версия | Что берём | Наши отклонения |
|---|---|---|---|
| [Semantic Versioning](https://semver.org/spec/v2.0.0.html) | 2.0.0 | формат `MAJOR.MINOR.PATCH`, правила bump, порядок версий | 0.x трактуем строже — см. §2 |
| [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) | 1.0.0 | `type(scope)!: описание`, футер `BREAKING CHANGE:` | список типов фиксирован — см. §3 |
| [Keep a Changelog](https://keepachangelog.com/en/1.0.0/) | 1.0.0 | структура `CHANGELOG.md`, `Unreleased`, группы | `Deprecated`/`Removed`/`Security` — вручную |

## 1. Принципы

1. **Релиз — осознанное действие, а не следствие merge.** Тег ставится, когда накопилось
   что показать пользователю и `main` зелёный, а не на каждый влитый PR.
2. **Тег — единственный источник версии.** Версия не дублируется в файлах вручную; все,
   кому она нужна (пакет, метаданные, окно «О программе»), получают её из тега при сборке.
3. **Черновик генерируется, финальный текст пишет человек.** Инструмент собирает список
   изменений из коммитов; заметки для пользователей не публикуются без правки.
4. **Автоматизируем механику, не суждение.** Версия, changelog, артефакты и триггеры
   сборки — машине. Что считать ломающим, что важно пользователю и когда релизить — человеку.
5. **Сборка воспроизводима и не ходит в сеть,** кроме загрузки исходников: это требование
   Flatpak и заодно страховка для OBS.
6. **Один тег — одна версия во всех каналах.** GitHub, OBS и Flathub получают артефакты
   из одного и того же тега; расхождение версий между каналами — дефект релиза.

## 2. Версия

Формат версии — [SemVer 2.0.0](https://semver.org/spec/v2.0.0.html)
([русский перевод](https://semver.org/lang/ru/)). Тег — `vMAJOR.MINOR.PATCH`, annotated
и подписанный (`git tag -s`). Префикс `v` обязателен: по нему git-cliff отличает
релизные теги от любых других (`tag_pattern`).

| Изменение | Коммит | 0.x | ≥ 1.0 |
|---|---|---|---|
| Ломающее | `type!:` или `BREAKING CHANGE:` | minor | major |
| Новое | `feat:` | minor | minor |
| Исправление | `fix:`, `perf:` | patch | patch |
| Внутреннее | `refactor:`, `docs:`, `test:`, `build:`, `ci:`, `chore:` | без релиза | без релиза |

- **До 1.0 ломающее изменение не поднимает major.** `1.0.0` — отдельное решение о
  стабильности, а не автоматическое следствие одного `!`.
- **Пользовательские данные — контракт.** Формат `settings.json` и `presets.json` меняется
  только с миграцией; иначе это ломающее изменение, даже в 0.x.
- **Пре-релизы** — `vX.Y.Z-beta.N`: GitHub prerelease, ветка `beta` на Flathub (после
  приёма в stable), подпроект `:testing` в OBS. В стабильный канал не попадают.
- **Build metadata (`+...`) в тег не пишем** — ломает сравнение версий в пакетных менеджерах.
- **До 1.0 поддерживаемой ветки нет:** исправления идут в `main` и в следующий релиз.
  Ветка `release/X.Y` заводится только после 1.0 и только если на стабильной линии есть
  пользователи; правило отбора исправлений в неё — отдельное решение того момента.
- **Тег не переиспользуется и не удаляется.** Ошибочный релиз исправляется новым patch-
  релизом; тег остаётся в истории (см. §5, «Откат»).

## 3. Коммиты и слияния

Формат сообщений — [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/),
английский — как в `AGENTS.md`. Спецификация разрешает любые типы; мы фиксируем список
ниже, чтобы версия и changelog были предсказуемы.

- Типы: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`.
- Scope — модуль: `window`, `view-panel`, `display`, `tab`, `tests`, `release`.
- Ломающее — `!` в типе (например, `feat(settings)!:`) и `BREAKING CHANGE:` в футере.
- Заголовок PR — conventional commit (уже закреплено в `AGENTS.md`).

**Слияние — squash.** Один PR = один коммит = одна строка changelog. Merge-коммиты
(«Merge pull request #N») в changelog не попадают и версию не двигают; при squash
это получается само, иначе это настраивается в парсере git-cliff.

Один PR — одно логическое изменение. Коммит `chore(release): vX.Y.Z` — единственный,
которому разрешено трогать сгенерированные файлы (`CHANGELOG.md`, метаданные).

## 4. Заметки: три поверхности

`CHANGELOG.md` ведётся по [Keep a Changelog 1.0.0](https://keepachangelog.com/en/1.0.0/):
раздел `Unreleased` сверху, версии с датами, группы `Added`/`Changed`/`Fixed`.
Группы `Deprecated`/`Removed`/`Security` добавляются вручную, если появятся.

| Артефакт | Кому | Язык | Кто пишет | Объём |
|---|---|---|---|---|
| `CHANGELOG.md` | разработчикам, упаковщикам | английский | генерируется | всё |
| GitHub Release | пользователям | русский | человек, из черновика | 5–10 пунктов |
| AppStream `<releases>` | центрам приложений, Flathub | английский (+ перевод) | человек | 3–6 строк |

Правила текста для пользователя:

- Строка отвечает на вопрос «что я теперь могу / что у меня перестало ломаться», а не
  «какой файл изменён». Без имён модулей, функций и внутренних терминов.
- Одно изменение — одна строка. Подробности — в PR и в `CHANGELOG.md`, не в релизной заметке.
- Если от пользователя требуется действие (переустановка, миграция настроек, смена
  зависимости) — отдельный блок **«Обновление»** в начале заметки.
- AppStream не умеет Markdown: только `<p>`, `<ul>/<li>`, `<em>`, `<code>`.
- Заметка пишется, пока контекст свеж: в design-документах уже есть пометки «в релиз-ноту»
  (например, `design/view-panel.md`), при релизе они переносятся в три поверхности выше.

## 5. Процесс выпуска

1. **Предусловия.** `main` зелёный (`invoke verify`), нет открытых блокеров релиза,
   рабочее дерево чистое, локальная ветка не отстаёт от `origin/main`.
2. **Черновик.** `invoke release --dry-run`: считает версию из коммитов, печатает
   группированный список изменений и предлагаемый текст заметок.
3. **Правка.** В релизный коммит входят: `CHANGELOG.md`, запись `<release>` в
   `io.github.frimn.volna.metainfo.xml`, при необходимости README и скриншоты в метаданных.
4. **Релизный коммит.** `chore(release): vX.Y.Z`, затем `git tag -s vX.Y.Z` и push ветки
   с тегом.
5. **CI по тегу.** Собирает источник (`git archive` / sdist), `SHA256SUMS`, подпись;
   создаёт **draft** GitHub Release и прикладывает артефакты.
6. **Публикация.** Человек правит заметки в draft-релизе, проверяет артефакты и публикует.
7. **OBS.** Webhook по тегу пересобирает пакет; проверить, что репозитории обновились
   и пакет ставится на целевых дистрибутивах.
8. **Flathub.** PR с новым тегом и хешем источника; дождаться сборки, установить и
   проверить запуск.
9. **Проверка после релиза.** `volna --version` совпадает с тегом; установка из каждого
   канала запускается; `appstreamcli validate` проходит.

### Откат

- Тег и релиз не удаляются и не переиспользуются. Ошибочный релиз помечается как
  проблемный (release notes / issue), исправление выходит следующим patch-релизом.
- В OBS и Flathub откат — это публикация предыдущей или исправленной сборки, а не
  удаление версии: удалённую версию пользователи уже могли поставить.
- Если сломано критично (данные, запуск), допускается снять артефакты из канала
  (unlisted/draft) и явно сказать об этом в issue.

## 6. Каналы доставки

| Канал | Артефакт | Обновления | Кто собирает |
|---|---|---|---|
| GitHub Releases | `volna-X.Y.Z.tar.gz` + `SHA256SUMS` + `.sig` | вручную | CI по тегу |
| OBS (`build.opensuse.org`) | rpm, deb, arch, flatpak-бандл | репозиторий OBS | OBS по webhook |
| Flathub | Flatpak `io.github.frimn.volna` | Flathub | Flathub |
| PyPI | — | — | — |

- **PyPI не используем.** Приложение ставится пакетным менеджером или Flatpak, а
  PyGObject берётся из системы; публикация wheel создала бы канал, который не работает
  без системных зависимостей. sdist при необходимости собирается, но не публикуется.
- **GitHub auto-archive (`/archive/refs/tags/...`) упаковщикам не отдаём:** в нём нет
  `.git`, и `hatch-vcs` вернёт `fallback-version = 0.0.0`. Источник для упаковки —
  приложенный тарбол или sdist.
- **OBS умеет собирать Flatpak** (`Type: flatpak`, манифест `flatpak.yaml`), но это
  бандл, а не канал обновлений. Обновления Flatpak — только Flathub или собственный
  OSTree-репозиторий; бандл из OBS годится для проверки сборки и ручной установки.
- **Flathub — не единственный канал.** Для файлового менеджера песочница ограничивает
  доступ к ФС; Flathub принимает такие приложения от upstream, но с оговорками. deb/rpm
  остаются основным каналом для дистрибутивов.
- **Заявку в Flathub открывает человек.** Политика Flathub запрещает агентам открывать
  или автоматизировать submission-PR и генерировать их тексты; манифест также не должен
  содержать AI-сгенерированного содержимого. Агент может подготовить черновики и
  проверить их, но авторство и отправка — за человеком.

## 7. Требования к сборке и упаковке

Пока их нет — релиз невозможен, поэтому это часть релизной готовности, а не «потом».

- **Метаданные приложения:** `io.github.frimn.volna.desktop`,
  `io.github.frimn.volna.metainfo.xml` (с `<releases>`, скриншотами, OARS, developer,
  brand color), иконка `io.github.frimn.volna.svg` в `hicolor/scalable/apps`.
  ID `io.github.frimn.volna` уже зашит в `Gtk.Application`; он же определяет Flathub-ID
  и меняется только через перезаявку — фиксируем его сейчас.
- **Install-интерфейс для упаковщиков:** `PREFIX`/`DESTDIR` (meson или Makefile),
  установка кода, `.desktop`, иконок, метаданных за одну команду.
- **Версия в сборке:** из тега. Для сборки из архива без `.git` — явно через
  `SETUPTOOLS_SCM_PRETEND_VERSION`; для meson-сборки — сгенерированный файл версии.
- **Зависимости для дистрибутивов:** Python ≥ 3.11, `python3-gi`/`python3-gobject`,
  `gir1.2-gtk-4.0`/`gtk4`, `gir1.2-graphene-1.0`. Python 3.10 (Ubuntu 22.04) не
  поддерживается — это ограничение `requires-python`, а не недосмотр.
- **`volna --version`** (и версия в «О программе») — иначе шаг 9 процесса нечем проверить.
- **Английская локализация UI** — требование Flathub к приёмке; без неё канал Flathub
  закрыт (исключение для автора-не-носителя возможно, но это отдельное решение).
- **Сборка без сети**, кроме загрузки исходников: pip в манифесте — только
  `--no-build-isolation` с заранее приложенными зависимостями, либо установка файлов
  напрямую.

## 8. Подпись и воспроизводимость

- **Ключ релизов** — отдельный GPG-ключ; отпечаток публикуется в README. Теги подписаны,
  CI проверяет подпись перед сборкой.
- **Контрольные суммы** — `SHA256SUMS` в каждом релизе; подпись сумм тем же ключом.
- **Воспроизводимость** — фиксированный `SOURCE_DATE_EPOCH`, `tar --sort=name`,
  стабильные mtime; сборка не зависит от даты и машины.
- **OBS и Flathub подписывают свои артефакты сами**; их ключи не смешиваются с ключом
  релизов.

## 9. Чего не автоматизируем

- Выбор версии в спорном случае (major/minor, «это вообще breaking?»).
- Текст заметок для пользователей и AppStream.
- Открытие submission-PR в Flathub и подачу в дистрибутивы (Debian, Fedora).
- Анонсы и решение «пора релизить».

## 10. Инструмент

**Решение:** [git-cliff](https://git-cliff.org) как движок + задача
`invoke release` + GitHub Actions, запускаемый по тегу.

- `git cliff --bumped-version` считает следующую версию из conventional commits;
  правила 0.x задаются в `cliff.toml` (`breaking_always_bump_major = false`).
- `invoke release` — тонкая обёртка: предусловия, версия, `CHANGELOG.md`, проверка
  `<release>` в метаданных, релизный коммит, подписанный тег, push. Вся логика версии
  остаётся в git-cliff, обёртка не изобретает SemVer.
- CI по тегу собирает артефакты и создаёт draft-релиз; OBS пересобирается по webhook.

**Проверено спайком** (git-cliff 2.14.2, клон репозитория, искусственный тег `v0.1.0`
на `163e67c`, конфигурация — `cliff.toml` в корне):

- два `fix` → `v0.1.1`; `feat` → `v0.2.0`; `feat!` в 0.x → `v0.2.0` (major не поднимается).
- без тегов нужен `initial_tag = "v0.1.0"`: без префикса `v` git-cliff падает
  с «does not match the tag pattern».
- «нечего релизить»: `--bumped-version` печатает текущую версию и выходит с кодом 0 —
  обёртка обязана сравнить результат с последним тегом и отказать.
- `--prepend` требует существующий `CHANGELOG.md`; при повторных запусках заголовок
  не дублируется.
- merge-коммиты отбрасываются как unconventional; русское сообщение коммита попадает
  в английский changelog как есть — язык коммитов надо держать.
- рендер работает без сети; нужен writable-кэш (`~/.cache/git-cliff-core`).

Почему не `semantic-release` (исходный план): он про публикацию пакета на каждый merge
в `main` — npm-плагины, `package.json`, релиз без гейта. У нас нет пакета, который надо
публиковать: тег запускает внешние сборки (OBS, Flathub). Полезная часть — «коммиты →
версия → заметки → тег» — у git-cliff та же, без Node-тулчейна и без релиза на каждый PR.

Почему не `release-please`: хорошая альтернатива, если хочется готовый release-PR без
своего кода. Но он обновляет версию в файле, а у нас версия — тег (`hatch-vcs`);
пришлось бы либо менять схему версионирования, либо держать второй источник версии.

Почему не `python-semantic-release`: Python-native, но версию в файле он тоже обновляет,
а поддержки VCS-версий (hatch-vcs) нет; релиз идёт без review-гейта.

| Инструмент | Версия из тега | Гейт перед релизом | Свой код | Заметки |
|---|---|---|---|---|
| git-cliff + invoke | да | да (`--dry-run`, тег вручную) | ~60 строк | шаблоны, любой формат |
| release-please | нет (нужен файл версии) | да (release-PR) | нет | только Markdown |
| semantic-release | да | нет (релиз на merge) | нет | только Markdown |
| python-semantic-release | нет | нет | нет | Markdown-шаблоны |

## 11. Решения и открытые вопросы

**Принято:**

- Инструмент — git-cliff 2.14.2 (`uvx git-cliff@2.14.2`) + задача `invoke release`
  + GitHub Actions по тегу. Release-PR и автоматический релиз на merge не используем.
- Версия — тег, единственный источник; `hatch-vcs` остаётся, статическая версия
  в `pyproject.toml` не вводится.
- Стандарты — SemVer 2.0.0, Conventional Commits 1.0.0, Keep a Changelog 1.0.0
  (см. таблицу в начале).
- PyPI — не публикуем; sdist собирается только как артефакт релиза.
- Ветка `release/X.Y` до 1.0 не заводится.
- Теги и релизы не удаляются и не переиспользуются.

**Открыто** (не меняет правила, но нужно до первого пакета):

- **Flathub:** идём или нет. Для файлового менеджера песочница — ограничение, приёмка
  требует английского UI; от решения зависит объём работ, но не §1–§9.
- **Целевые дистрибутивы OBS:** openSUSE Tumbleweed, Fedora, Debian stable, Ubuntu LTS —
  выбрать перед первой сборкой пакета.

## 12. Риски

| Риск | Влияние | Что делаем |
|---|---|---|
| Flathub: файловый менеджер в песочнице | отказ или урезанный UX канала | Flatpak не основной канал; проверить доступ к ФС до инвестиций в заявку |
| Flathub требует полной английской локализации UI | канал закрыт без gettext | решить до заявки: локализация или отказ от Flathub |
| Политика Flathub про AI: манифест не должен быть AI-generated, агенты не открывают submission-PR | отказ/бан при нарушении | манифест пишет человек, PR открывает человек; агент — только черновики и проверки |
| `hatch-vcs` + архив без `.git` | версия `0.0.0` в пакете | отдавать тарбол/sdist, `SETUPTOOLS_SCM_PRETEND_VERSION`, проверять `volna --version` в каждой сборке |
| Нет install-интерфейса и метаданных приложения | пакет не собрать ни в OBS, ни в Flatpak | считать release readiness: `PREFIX`/`DESTDIR`, `.desktop`, metainfo, иконка |
| Merge-коммиты и сообщения не на английском | шум и смешанный язык в changelog | squash, английский по `AGENTS.md`, проверка в ревью; спайк уже поймал русский коммит |
| Свой клей `invoke release` (~60 строк) | баг в релизном скрипте ломает выпуск | системные тесты, `--dry-run` по умолчанию, тег ставится только вручную |
| Версия git-cliff не закреплена | изменение поведения между релизами | пин `git-cliff@2.14.2` в задаче и CI, обновление — осознанно |
