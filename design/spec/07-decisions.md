# 07 · Журнал дизайн-решений

Формат: решение → контекст → следствие. Решения приняты по референсам Dolphin/JetBrains, затем скорректированы фидбеком (ревизии 2–3). Отклонённые варианты сохранены, чтобы не «переизобретать» их позже.

## D01 · Три направления, выбор C

- **Контекст:** нужны варианты дизайна файлового менеджера по двум референсам — Dolphin и JetBrains.
- **Решение:** сделать A (Dolphin-верный), B (JetBrains Workbench), C (гибрид); развивать C.
- **Следствие:** A/B остаются эталонами (верность референсу / панельная грамматика и light-тема), C — боевая спека.
- **Отклонено:** один «средний» вариант без сравнения — не даёт выбора и теряет сильные стороны референсов.

## D02 · Токены JetBrains, контент Dolphin

- **Решение:** хром/панели/типографика — JetBrains New UI; данные, «Столбцы», Places, фильтр/зум, характер — Dolphin.
- **Следствие:** тёмная палитра `#1e1f22/#2b2d30/#393b40/#3574f0`; папки — синий контент; внутри окна нет градиентов/теней.

## D03 · Убрать дубли контролов

- **Контекст:** в первых макетах дублировались тема, настройки, поиск/фильтр, вид и сортировка.
- **Решение:** один контрол на функцию: одна тема, одна шестерёнка (в тулбаре), одно поле поиска в «Местах», одно поле фильтра в редакторе, один «Вид» (в нём — режим, группировка, сортировка, масштаб), один терминал — **нет терминала**.
- **Следствие:** тулбар разгружен, рейлы без settings/terminal, правый рейл — только «Сведения/Предпросмотр».
- **Отклонено:** тема в двух местах, view-тогглы в тулбаре и редакторе одновременно, сортировка в двух местах.

## D04 · Удалить терминал

- **Контекст:** терминал не нужен пользователю.
- **Решение:** удалить полностью: нет кнопок в рейлах, нет вкладки/панели внизу, нет пункта меню «Открыть в терминале», нет терминальных строк/JS.
- **Следствие:** нижняя панель — только «Операции / Журнал».

## D05 · «Вместо «Столбцы» — окно «Вид»»

- **Контекст:** контрол «Столбцы» показывал текущий режим и открывал меню режимов — этого мало и это дублирует переключатели.
- **Решение:** единая кнопка **«Вид»**, открывающая поповер с настройками отображения: режим, группировка, сортировка, параметры, масштаб.
- **Следствие:** нет отдельного виджета «Столбцы»; режим — radio в «Вид»; статус-бар больше не показывает режим.

## D06 · «Вид» — слева от пути

- **Контекст:** путь бывает разной длины; кнопка «Вид» справа от него «прыгала».
- **Решение:** порядок `☰ · навигация · «Вид» · путь (flex) · настройки · контролы окна`; «Вид» зафиксирован, путь растягивается и усекается.
- **Следствие:** предсказуемая позиция; путь — единственный гибкий элемент.

## D07 · Путь только сверху + редактирование

- **Контекст:** путь дублировался в статус-баре; нужна навигация вводом адреса.
- **Решение:** путь только в тулбаре; кнопка-карандаш открывает inline-редактор (Enter — переход по известному пути, Esc/blur — отмена, неизвестный путь — заметка «Путь недоступен»).
- **Следствие:** статус-бар свободен для статуса; путь инициирует «Сканирование…».

## D08 · Все три режима — настоящие

- **Контекст:** в первой версии C только «Столбцы» были реализованы, остальные — заглушки.
- **Решение:** «Значки» (сетка с секциями), «Столбцы» (текущий), «Подробности» (таблица с sticky-шапкой); общий диспетчер `renderBand`.
- **Следствие:** «Вид → Режим просмотра» переключает реальные представления; данные/фильтр/сортировка/выделение общие.

## D09 · Группировка в «Вид»

- **Контекст:** группировка по дате — часть референса, но должна быть управляемой.
- **Решение:** секция «Группировка»: «По дате изменения» (default) / «Без группировки».
- **Следствие:** без группировки — плоские списки/сетки, безголовые колонки по 6 строк; сортировка глобальная.

## D10 · Масштаб — в «Вид», не в статус-баре

- **Контекст:** зум в статус-баре занимал место, дублировал настройки отображения и мешал «статусному» статус-бару.
- **Решение:** слайдер в секции «Масштаб» поповера «Вид»; в статус-баре удалён.
- **Следствие:** зум влияет на «Значки» и «Столбцы»; «Подробности» сохраняют стандарт 24px.

## D11 · Статус-бар: статус + диск/устройство

- **Контекст:** пользователь попросил слева только статус, рядом со свободным местом — имя устройства.
- **Решение:** слева «Сканирование…» → «Готово.»; справа `свободно 22,8 ГиБ · sdc1`; убраны путь, счётчики, зум, режим.
- **Следствие:** счётчики остались в тулбаре редактора; статус — live-регион.

## D12 · Устройство рядом со свободным местом

- **Решение:** показывать `sdc1` после индикатора свободного места (mono, 13px).
- **Следствие:** в продукте — имя точки монтирования; в макете статично.

## D13 · Инспектор сохраняет путь

- **Контекст:** в инспекторе «Сведения» есть строка «Путь»; пользователь просил убрать путь только из статус-бара.
- **Решение:** оставить путь в метаданных инспектора (это свойство объекта, не навигационный контрол).
- **Следствие:** путь встречается в тулбаре (навигация) и в свойствах объекта — это не дубль контрола.

## D14 · Поповер, а не модальное окно настроек

- **Контекст:** Dolphin использует диалог «Режим просмотра», JetBrains — поповеры.
- **Решение:** в C — поповер 320px с живым применением; модальный диалог остаётся только в A (как верность референсу).
- **Следствие:** быстрее переключение, нет блокировки контента, проще переносить в продукт.

## D15 · Светлая тема не входит в C

- **Контекст:** B реализует light (тёмный тулбар + светлые панели).
- **Решение:** C — только тёмная; light-токены зафиксированы в спеке как референс для будущего.
- **Следствие:** не смешиваем две темы в одном макете; light внедрять отдельным этапом по B.

## D16 · Прототип, а не продукт

- **Решение:** артефакт — самодостаточный HTML, данные демонстрационные, окно масштабируется; прототип не содержит реального I/O.
- **Следствие:** спека описывает поведение и метрики, а не реализацию системных вызовов.

## D17 · Пресеты отображения в «Вид»

- **Контекст:** пользователь попросил выбор пресета с кнопкой сохранения и диалог выбора/ввода имени.
- **Решение:** секция «Пресеты» вверху поповера: поле выбора (инлайн-список) + кнопка сохранения. Пресет — снапшот `{viewMode, grouping, sort, sortDir, showHidden, compact, zoom}`; 4 встроенных пресета; применение мгновенное, с обновлением всех контролов.
- **Следствие:** ручные изменения показывают «Настроено вручную»; диалог сохранения позволяет выбрать существующее имя (перезапись) или ввести новое; кастомные пресеты перекрывают встроенные по имени.
- **Отклонено:** пресеты как отдельное модальное окно; выпадающее меню вне поповера; автосохранение без имени.

## D18 · Пользовательские пресеты — в localStorage

- **Контекст:** «сохранение» имеет смысл только если пресет доступен позже; при этом состояние окна намеренно не персистится.
- **Решение:** кастомные пресеты — `localStorage['volna.presets.v1']`; встроенные не персистятся; при недоступности storage — память. Остальное состояние (режим/фильтр/вкладка) при перезагрузке сбрасывается.
- **Следствие:** пресеты переживают reload; данные макета остаются демонстрационными; try/catch защищает file:// и приватные режимы.
- **Отклонено:** полная персистенция всего состояния (противоречит прототипу); серверное хранение (вне scope).

## D19 · Переименование и удаление — только для пользовательских пресетов

- **Контекст:** пользователь попросил удаление/переименование пресетов из списка.
- **Решение:** действия (карандаш/корзина) показываются у кастомных пресетов; встроенные — неизменяемые дефолты. Кастомный пресет, перекрывающий встроенный по имени, считается кастомным и редактируется/удаляется; после удаления встроенный снова виден.
- **Следствие:** дефолты нельзя «сломать»; встроенный можно перекрыть сохранением под тем же именем. Действия появляются на hover/`focus-within`, доступны с клавиатуры.
- **Отклонено:** редактирование встроенных на месте; удаление встроенных; скрытые иконки без доступа с клавиатуры.

## D20 · Инлайн-переименование + подтверждение удаления

- **Контекст:** нужны быстрые действия из списка, но удаление необратимо.
- **Решение:** переименование — inline-input в строке (Enter/Esc/blur, валидация пустого/дубля); удаление — модальное подтверждение с безопасным фокусом на «Отмена» и опасной кнопкой `#db5c5c`.
- **Следствие:** переименование не трогает снапшот настроек и id; удаление текущего пресета переключает на «По умолчанию»; список/поповер остаются открыты.
- **Отклонено:** удаление без подтверждения; переименование через отдельный диалог; drag-and-drop сортировка (вне scope).

## Отклонено и почему

| Идея | Почему нет |
|---|---|
| Finder-подобный column browser (выбор задаёт следующую колонку) | ломает датовые колонки Dolphin, другой продукт |
| Терминал в нижней панели | не нужен пользователю |
| Дубли темы/настроек/поиска/вида | шум, непредсказуемость, нарушает принцип «один контрол — одна функция» |
| Кнопки режимов вида в тулбаре редактора | дубль с «Вид»; редактор должен быть чистым |
| Зум в статус-баре | статус-бар = состояние, зум = настройка отображения |
| Путь в статус-баре | дубль с тулбаром; статус-бар перегружен |
| Модальный диалог настроек вида в C | медленнее и противоречит JetBrains-грамматике |
| Заглушки вместо режимов | противоречит «все режимы настоящие» |
| Светлая тема в C | вне объёма; риск смешать две палитры |

## D21–D26 · Ядро перечисления и сортировки

Решения по архитектуре ядра (подробно — [09-core-architecture.md](09-core-architecture.md)).

### D21 · Ядро на Python, Rust — точечно после бенчмарка

- **Контекст:** нужно перечислять каталоги до сотен тысяч записей; рассматривался Rust.
- **Решение:** ядро на чистом Python (`os.scandir`/`os.stat` — это и так C/ядро; `stat`-фаза параллелится пулом потоков, т.к. `os.stat` отпускает GIL). Rust добавляется только за узким контрактом `stat_batch` (PyO3) и только если бенчмарк на 100k+ покажет выигрыш.
- **Следствие:** нет toolchain/сборки/FFI-границы на старте; escape hatch зафиксирован, слои выше не меняются.
- **Отклонено:** сразу Rust-ядро (PyO3) и Rust-демон + IPC — до измерения достаточности (п. 4, 8 AGENTS.md).

### D22 · Сходящийся порядок + порог

- **Решение:** до `STREAMING_THRESHOLD = 50_000` — один полный `readdir+stat+sort`; выше — потоковое схождение (батчи копятся, полный `list.sort()` по троттлу, timsort адаптивен).
- **Следствие:** порядок гарантирован с первого кадра на обычных каталогах, UI отзывчив на огромных; статус «Сканирование…» честный.
- **Отклонено:** всегда полная сортировка до показа (держит «Сканирование…» на 100k+); `bisect.insort` на каждый элемент (O(n²) сдвигов).

### D23 · Двухфазное перечисление

- **Решение:** фаза 1 — `d_type` из `getdents64` (тип бесплатно, без `stat`); фаза 2 — ленивый/параллельный `statx` для размера/даты, только для нужного представления.
- **Следствие:** мгновенный первый кадр (имена/типы/сортировка по имени); «Подробности» и бакеты дат заполняются по мере готовности метаданных.
- **Отклонено:** безусловный `stat` на каждую запись (медленно на `ls -l`-сценарии, теряет мгновенный показ).

### D24 · DirModel — единый источник порядка

- **Решение:** порядок, группы по дате и счётчики живут в одной модели и сходятся по мере прихода батчей; группы/счётчики — производные, не отдельные коллекции.
- **Следствие:** три режима и фильтр/выделение работают над одним источником истины; нет рассинхрона порядка между «Столбцами» и «Подробностями».

### D25 · Виртуализация на GTK

- **Решение:** виртуализацию обеспечивает `Gtk.ListView`/`GridView`; изменения модели сливаются батчами через `Gio.ListStore.splice()`, фильтр — `Gtk.FilterListModel`.
- **Следствие:** виджеты создаются только для видимой области; нет ручного «отправить на отрисовку» сотен тысяч строк.
- **Отклонено:** собственная виртуализация/вручную управляемые списки виджетов.

### D26 · Без персистентного кэша метаданных листинга

- **Контекст:** обсуждалось хранение размера/дат каждого каталога во встроенной БД (SQLite) с чтением кэша при открытии и последующим обновлением из ФС.
- **Решение:** персистентного кэша метаданных **листинга** не заводим. Быстрая часть (имена+типы) и так бесплатна из `d_type`; дорогая часть (`size`/`mtime`) не валидируется по `mtime` каталога (содержимое файла меняется без изменения каталога) — значит либо заново `stat`ить, либо ловить `inotify`, что сводит выгоду на нет. Вместо этого: (1) сессионный LRU листингов в памяти, ключ `(path, dir_mtime)`; (2) `inotify` только на открытых каталогах; (3) отдельный опциональный слой для дорогих вещей (размер папок, миниатюры, позже — индекс поиска).
- **Следствие:** нет второй БД как источника истины, нет риска устаревших размеров/дат; встроенная БД (SQLite FTS5/Tantivy) оправдана только для индекса поиска и кэша размеров папок/миниатюр, каждый — с контрактом устаревания и возможностью пересобрать с нуля (п. 14 AGENTS.md).
- **Отклонено:** персистентный per-directory кэш размера/дат как основной путь; доверие кэшу без валидации; рекурсивная подписка `inotify` на всё дерево (упирается в лимиты ядра `max_user_watches`/`max_user_instances`).

### D27 · Масштаб интерфейса следует за рабочим столом

- **Контекст:** интерфейс был нарисован в «широком» пресете ×1.25, откалиброванном по `reference/pycharm.png` — скриншоту IDE на 125 %-десктопе. Пресет захардкодили как дефолт, поэтому на 100 %-десктопе (10 pt, 96 dpi) приложение выглядело на 20–30 % крупнее соседних приложений: хром 50 px против 38–43, кегль 17.5 px против 13.3. Вдобавок CSS жёстко задавал `font-family` (первым находился Ubuntu вместо системного Noto Sans) и `font-size` в px, так что системный шрифт и DPI на интерфейс не влияли.
- **Решение:** масштаб `s` считается по системному UI-кеглю (`s = кегль системы / эталон 10 pt @ 96 dpi`), корневой кегль приложения — `14 px × s`. CSS переведён на одну компактную сетку в `em` (1em = 14 px при 100 %), пиксельная геометрия в Python — через `size.px()`. Семейство и кегль шрифта наследуются от GTK/системы; `font-family` в теме не задаётся. 1px-линии и радиусы не масштабируются.
- **Следствие:** на 100 %-десктопе приложение компактное (хром 40, окно 1440×900), на 125 % — ровно широкий пресет дизайна (хром 50, окно 1800×1125), на 150 % и промежуточных масштабах — та же сетка без нового CSS. «Широкий» и «компактный» остаются референсными точками, а не жёстким дефолтом; ручной оверрайд размера — будущая настройка.
- **Отклонено:** оставить хардкод ×1.25 и переключать пресет вручную (не решает 100 %-десктопы); грузить Inter в приложение (нарушает системный вид и лишний ресурс); масштабировать по разрешению монитора (не учитывает системный кегль и accessibility).
