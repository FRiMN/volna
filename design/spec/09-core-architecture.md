# 09 · Архитектура ядра (перечисление и сортировка каталогов)

Реализационная спека **ядра** файлового менеджера: как «Волна» открывает и показывает каталоги произвольного размера (вплоть до сотен тысяч записей), не блокируя UI. Дополняет [06-implementation.md](06-implementation.md) (§9 — ограничения прототипа) и [07-decisions.md](07-decisions.md): прототип заменяется реальным I/O, но три режима просмотра («Значки»/«Столбцы»/«Подробности») и их поведение из [04-components.md](04-components.md) и [08-acceptance.md](08-acceptance.md) остаются контрактом, который это ядро обязано кормить.

**Статус:** черновик архитектуры ядра, версия 0.1. Пороги и метрики — стартовые значения, подлежат замеру (см. §14 и решения D21–D26 в [07-decisions.md](07-decisions.md)).

---

## 1. Границы ядра

Ядро отвечает за **данные и их порядок**, но не за пиксели:

| Входит в ядро | Не входит (слой UI) |
|---|---|
| перечисление записей каталога | виджеты трёх режимов (grid/columns/table) |
| метаданные (тип, размер, mtime) | раскладка, зум, плотность |
| порядок (сортировка) и группы (по дате) | выделение, скролл, фильтр-поле как виджет |
| счётчики («127 папок · 19 файлов …») | пресеты отображения, «Вид»-поповер |
| отмена/повтор, статус скана | свободное место и статус-бар как контролы |

Граница проходит по **модели**: ядро публикует события об изменениях, UI подписывается и отрисовывает. Ядро не знает про `Gtk.ListView` и не должно импортировать GTK (кроме `GObject`-событий, если понадобятся) — по образцу существующего `src/volna/geometry.py` («без GTK-импортов»).

## 2. Слои и поток данных

```
┌ UI (GTK4) ── Gtk.ListView / GridView + Gio.ListStore + FilterListModel ─┐
│        ▲  события: item-batch / order-changed / group-changed /         │
│        │           counters-changed / scan-state / error                │
├ Model (DirModel) ── сходящийся порядок, группы, счётчики, поколение ────┤
│        ▲  батчи Entry[]                                                 │
├ Scanner (DirScanner) ── readdir-батчи, параллельный stat, отмена ───────┤
│        ▲  readdir (d_type) + statx / io_uring                           │
└ ОС: getdents64 → d_type; statx → size/mtime ─────────────────────────────┘
```

Четыре слоя; между соседними — узкий контракт. Направлений два: **вниз** (управление: открыть путь → начать скан → читать) и **вверх** (данные: dirent → `Entry` → диффы в UI). Подробнее — диаграмма [`../../.archify/architecture-volna-core-20261114-233600/volna-core.html`](../../.archify/architecture-volna-core-20261114-233600/volna-core.html).

## 3. Модель данных: `Entry`

```python
# src/volna/core/entry.py — чистый dataclass, без GTK
@dataclass(slots=True)
class Entry:
    name: str              # basename
    path: str              # абсолютный путь
    kind: Kind             # DIR | FILE | SYMLINK | OTHER — из d_type, бесплатно
    size: int | None       # None, пока stat не выполнен
    mtime: float | None    # None, пока stat не выполнен
    # ключи сортировки, вычисляются один раз при вставке:
    name_key: str          # casefold(name) — для сортировки по имени
```

Правила:

- **`kind` из `d_type`** (`entry.is_dir()`/`is_file()`/`is_symlink()`), а не из `stat` — это нулевой по стоимости первый проход, см. §4.
- **`size`/`mtime` опциональны.** Пока не получены — сортируются «в конец», в деталях показываются «—». Это и есть механика «Сканирование…» из макета: строка есть, метаданные приходят позже.
- **Ключи предвычислены.** Сортировка оперирует только ключами, не вызывая `stat` повторно и не пересчитывая регистр.

Сортировочный компаратор — чистая функция в `core/order.py` (без GTK), чтобы её можно было юнит-тестировать без дисплея:

```python
# src/volna/core/order.py
def entry_key(e: Entry, *, key: SortKey, dir_: bool) -> tuple:
    """Папки первыми; — и 0 Б в конец; стабильно по (ключ, name_key)."""
```

Контракт сортировки (наследуется из [08-acceptance.md](08-acceptance.md) §4): папки выше файлов, направление (`asc`/`desc`), `«—»` и `0 Б` всегда в конце, порядок стабильный.

## 4. Двухфазное перечисление

`getdents64` (а значит `os.scandir`) уже отдаёт записи **буфером**, не по одной, и даёт `d_type` на ext4/xfs **без отдельного `stat`**. Поэтому:

- **Фаза 1 (быстрая):** `os.scandir(path)` → `Entry` с `name`/`kind`/`name_key`, `size=None`, `mtime=None`. Даёт мгновенный первый кадр: имена, типы, сортировку по имени. На каталоге 100k — доли секунды.
- **Фаза 2 (ленивая, параллельная):** для записей, которым нужны `size`/`mtime` (режим «Подробности», сортировка по размеру/дате, группировка по дате) — `statx` через `StatPool` (§5). Результаты приходят партиями, колонки и группы заполняются по мере готовности.

Правило: **не `stat`ить то, что не нужно для текущего представления.** Сортировка по имени в «Значках» не требует ни одного `stat`.

## 5. `StatPool` — параллельные метаданные

`core/statpool.py`:

```python
class StatPool:
    def submit(self, entries: list[Entry]) -> None: ...   # chunk-и по N
    def close(self) -> None: ...
```

- `os.stat`/`DirEntry.stat` **отпускают GIL** на время системного вызова, поэтому пул потоков даёт реальный параллелизм на `stat`-фазе (в отличие от сортировки, которая GIL-связана, но дёшева).
- Стартово: `concurrent.futures.ThreadPoolExecutor(max_workers=8)`, чанки по 256 путей.
- Результат возвращается в сканер; сканер собирает `Entry` целиком и отдаёт модели. Колонка `size`/`mtime` и бакет даты проставляются только здесь.
- Позже пул можно заменить на `io_uring` без изменения контракта (§10).

## 6. Батчи: две разные порции

Слово «батч» в постановке означало две разные вещи — фиксируем их раздельно:

| Батч | Где | Зачем | Стартовое значение |
|---|---|---|---|
| **I/O-порция** | Scanner | не «съедать» цикл и не держать всю очередь в памяти; backpressure | читать порциями времени (~2–4 мс) или по 1024 dirent |
| **render-порция** | Model → UI | слить изменения до перерисовки, чтобы не было repaint на каждую строку | троттл ~16–33 мс (кадр) или граница батча |

Правила:

- Scanner собирает `dirent` в порции и отдаёт `list[Entry]` в модель; порция не обязана совпадать с буфером `readdir`.
- Model копит пришедшие `Entry`, **не** пересортировывает на каждую вставку, а сливает изменения в UI через `Gio.ListStore.splice()` (батч-вставка), не `insert()` по одному.
- Счётчики и группы обновляются инкрементально, а не пересчётом всего списка.

---

## 7. Сортировка: сходящийся порядок + порог

Глобальная сортировка требует увидеть **все** записи; «сортировать каждый батч» даёт только локально отсортированные порции. Решение (D22):

- **До порога** `STREAMING_THRESHOLD = 50_000` (настраиваемо): прочитать + `stat` (по необходимости) + один полный `list.sort()`. Синхронно, быстро, порядок гарантирован с первого кадра.
- **Выше порога** — потоковое схождение: батчи копятся в `list`, полный `list.sort()` вызывается по троттлу/границе батча. Timsort на почти-отсортированных данных адаптивен (~O(n)); UI показывает *сходящийся* порядок, статус — «Сканирование…» до первого стабильного состояния.

Почему не `bisect.insort` на каждый элемент: O(n²) сдвигов на 100k. Периодический полный `sort()` проще и на практике быстрее.

**Группировка по дате** — производная модель: бакет (`Сегодня/Вчера/…`) назначается, когда приходит `mtime`. До этого запись может быть в «неопределённой» группе; при приходе `mtime` модель эмитит `group-changed`. Состав группы «дозревает» так же, как порядок.

## 8. Поток выполнения, отмена, идемпотентность

```python
# src/volna/core/scanner.py
class DirScanner:
    def start(self, path: str, generation: int) -> None: ...
    def cancel(self) -> None: ...
```

- **Рабочий поток:** скан идёт в `threading.Thread`; батчи перекладываются в очередь, главный поток вычитывает её через `GLib.idle_add`. UI-поток никогда не блокируется.
- **Поколение (`generation`):** монотонно растущий int. Каждый батч несёт своё поколение; модель принимает батчи только с `generation == current`, иначе отбрасывает. `open(path)` инкрементирует поколение и выставляет `threading.Event` для кооперативной отмены старого скана (тот проверяет Event между порциями и выходит).
- **Идемпотентность:** повторный `open(path)` — это просто новый скан; «устаревший» результат не может перезаписать новый (п. 17, 28 из AGENTS.md).
- **Статус-канал:** `scan-state(SCANNING → READY | ERROR)` — честный канал для статус-бара вместо таймера из макета ([06-implementation.md](06-implementation.md) §9, рекомендация 6 из §10).

Ошибки (`PermissionError`, «каталог исчез», «не каталог») — событие `error(path, exc)`, не падение и не пустой молчаливый экран.

## 9. Счётчики и свободное место

- **Счётчики** (`папок/файлов/суммарный размер`) — инкрементальные: счётчик типов растёт на фазе 1, суммарный размер — по мере прихода `stat` на фазе 2. Эмитятся через `counters-changed`.
- **Свободное место и устройство** — отдельный `os.statvfs(path)`, кэшируется, не зависит от скана; обновляется по требованию/таймеру. Это то, что в макете было статично (`22,8 ГиБ · sdc1`).

---

## 10. Виртуализация и фильтр (слой UI, но контракт — отсюда)

- **Виртуализация отдаётся GTK:** `Gtk.ListView`/`Gtk.GridView` создают виджеты только для видимой области. Модель синхронизируется с `Gio.ListStore` через батч-`splice`; «отрисовывать сотни тысяч строк» руками не нужно.
- **Фильтр** (live, case-insensitive) — `Gtk.FilterListModel` с кастомным `Gtk.CustomFilter` по `name_key`; он не трогает порядок модели и не пересортировывает.
- **Выделение** — `Gtk.SingleSelection`/`MultiSelection` поверх фильтра; выбор не сбрасывается при перерисовке (контракт из [08-acceptance.md](08-acceptance.md) §4).
- Три режима — три фабрики строк над **одним и тем же** `DirModel` (диспетчер рендера из D08); данные, порядок и группы общие.

## 11. Модульная структура

```
src/volna/
  core/
    entry.py      # Entry, Kind — чистые dataclass/enum
    order.py      # компаратор и ключи сортировки — без GTK
    scanner.py    # DirScanner: readdir-батчи, поколение, отмена
    statpool.py   # параллельный statx (пул потоков → io_uring)
    model.py      # DirModel: порядок, группы, счётчики, события
  views/
    icons.py      # «Значки» (фабрика строк Gtk.GridView)
    columns.py    # «Столбцы»
    details.py    # «Подробности»
```

`core` — без GTK-импортов (тестируется без дисплея), `views` — единственное место, где UI знает про GTK. Политики (порог, размеры батчей, число потоков) — константы/конфиг, отделённые от механизма (п. 10 AGENTS.md).

## 12. Кэш метаданных (D26)

Персистентный кэш размера/даты **листинга** не заводим. Причины:

1. **Быстрая часть бесплатна:** имена и типы приходят из `d_type` без `stat` (§4).
2. **Дорогую часть нельзя провалидировать:** `mtime` каталога меняется при добавлении/удалении/переименовании, но не при изменении содержимого файла. Размер файла меняется без изменения каталога → кэш размера валидируется только повторным `stat`, что обесценивает кэш.
3. **Устаревшие размеры/даты хуже медленного показа:** ФМ — инструмент, чья работа показывать актуальное состояние (риск удалить не то, [01-product-direction.md](01-product-direction.md) §4).
4. **Ядро уже кэширует:** page cache делает тёплый повторный `readdir+stat` быстрым, а холодный первый показ кэш всё равно не ускорит.

Принцип: **ФС — уже БД и единственный источник истины; вторая БД допустима только как расходуемый ускоритель с явным контрактом устаревания** (п. 13–14, 32 AGENTS.md).

Вместо персистентного кэша листинга:

- **Сессионный LRU в памяти** (без БД): последние N листингов, ключ `(path, dir_mtime)`. Возврат назад/вперёд — мгновенно; при расхождении `mtime` — перечитать. Дёшево и всегда корректно.
- **`inotify` только на открытых каталогах** (как Nautilus), не рекурсивно на всё дерево — иначе упираемся в лимиты ядра (`max_user_watches`/`max_user_instances`); вотчи добавляем по требованию при открытии.
- **Отдельный опциональный слой** для дорогих и «приблизительных» вещей: размер папки (рекурсивный `stat`, показывать как «~», пересчёт фоном), миниатюры (ключ `(inode, size, mtime)`), позже — индекс поиска. Каждый со своим контрактом устаревания и возможностью пересобрать с нуля.

Встроенная БД (SQLite FTS5 / Tantivy / Xapian) оправдана как раз для **индекса поиска** и, возможно, кэша размеров папок/миниатюр — но не для листинга.

## 13. Rust: точечный escape hatch

Ядро — на Python (D21). Rust добавляется **только** если бенчмарк покажет, что `stat`-фаза в Python — бутылочное горлышко, и **только** за узким интерфейсом:

```python
# стабильный контракт, за которым может жить и пул потоков, и PyO3-расширение
stat_batch(paths: list[str]) -> list[StatResult]   # (size, mtime, ...)
```

Условие включения — измеренный выигрыш на реальном каталоге 100k+ (п. 4 AGENTS.md), а не «Rust быстрее» априори. Если включаем — это PyO3-расширение под тем же `StatPool`-интерфейсом, без изменения слоёв выше.

## 14. Нефункциональные требования (стартовые, подлежат замеру)

| Метрика | Цель | Как проверяется |
|---|---|---|
| Первый кадр (имена/типы) на 100k | < 500 мс | системный тест с фикстурой 100k |
| Полный `stat`+сортировка на 100k | < 3 с, UI без фризов | то же + замер кадрового времени |
| Память на 100k | < 150 МБ сверх базы | tracemalloc/RSS |
| Отмена при быстрой навигации | старая порция не «выигрывает» | тест: 5× `open` подряд, порядок = последний путь |
| Идемпотентность | повторный `open(path)` = чистый новый скан | тест двойного вызова |
| Статус-канал | `SCANNING → READY` ровно один раз | тест последовательности событий |

Пороги — стартовые; перед приёмкой прогоняются и калибруются бенчмарком (п. 2, 6 AGENTS.md). Функциональная приёмка ядра — пересечение с [08-acceptance.md](08-acceptance.md) §4–5 (сортировка/группировка/счётчики/фильтр во всех трёх режимах).

## 15. Решения

Приняты D21–D26, зафиксированы в [07-decisions.md](07-decisions.md) (журнал продолжает нумерацию):

- **D21** — Python-first; Rust точечно за `stat_batch` после бенчмарка.
- **D22** — сходящийся порядок + порог `STREAMING_THRESHOLD`.
- **D23** — двухфазное перечисление (`d_type` быстрый проход + ленивый/параллельный `statx`).
- **D24** — `DirModel` — единый источник порядка; группы и счётчики — сходящиеся производные.
- **D25** — виртуализация на GTK (`Gio.ListStore.splice`), не ручной рендер.
- **D26** — без персистентного кэша метаданных листинга; сессионный LRU + `inotify` на открытых; БД — только под поиск/дорогие кэши.
