# «Режимы просмотра» — проект режимов «Столбцы» и «Значки» (V2)

**Статус:** реализовано (2026-11-16). Основание: спека [design/spec](spec/README.md) v1.5, канонический макет [`design/artifacts/variant-c.html`](artifacts/variant-c.html). Три режима разделены: по модулю на режим (`views/<mode>.py`), общий контракт `ListingView`, реестр `MODE_VIEWS`, диспетчер в `DirectoryTab`, секция «Режим просмотра» в панели. Группировка реализована следующей итерацией — [grouping.md](grouping.md) (2026-11-17); масштаб, пресеты — вне этой итерации (§12).
**Предмет:** три режима просмотра листинга — «Подробности» (есть), «Столбцы» и «Значки» (новые), — разделённые так, чтобы будущий четвёртый режим был добавлением одного модуля.
**Не предмет (эта итерация):** группировка по дате, масштаб (zoom), пресеты, колонка «Тип», выделение и инспектор.

Решения владельца (2026-11-16) и их следствия:

| Вопрос | Решение | Следствие |
|---|---|---|
| Группировка по дате | **не входит** в итерацию | режимы плоские; заложен шов «секции», но он всегда один и безымянный |
| Масштаб (zoom) | **отложен** | поле `zoom` остаётся (=50), слайдера нет, `zoom_modes` пуст |
| Переключатель режима | **только поповер «Вид»** | один контрол на функцию (D05 из [07-decisions](spec/07-decisions.md)); иконка триггера статична |
| Режим по умолчанию | **«Подробности»** | поведение при первом запуске не меняется |

Осознанное расхождение с макетом: в макете «Столбцы» — это колонки **по группам дат**, а «Значки» — сетки по группам. В этой итерации группировки нет, поэтому «Столбцы» — безголовые колонки, а «Значки» — одна сетка ([04-components §6.2](spec/04-components.md)). Макет остаётся эталоном для метрик и раскладки; расхождение закрывается итерацией группировки (§12).

## 2. Ключевые решения

### D1. Режим = модуль + одна строка реестра

Каждый режим — отдельный модуль `views/<mode>.py` с одним классом, наследующим общий контракт. Реестр — **явный кортеж** в `views/registry.py`; порядок и состав видны в одном месте.

```python
# src/volna/views/registry.py
MODE_VIEWS: tuple[type[ListingView], ...] = (IconsView, ColumnsView, DetailsView)
VIEWS_BY_MODE: Mapping[ViewMode, type[ListingView]] = {view.mode: view for view in MODE_VIEWS}
```

Почему так, а не иначе:

- Режим — это **разница в раскладке**, а не разница в данных. Данные одни и те же (`DirModel`), отличается только виджет-дерево. Значит, режим — это класс с общим контрактом, а не ветка в `if mode == ...` (иначе через год получим 400 строк `elif`-ов в `tab.py`).
- Реестр — **явный кортеж**, не `importlib`/`entry points`: нет скрытой композиции, нет зависимости от факта установки пакета, состав виден при чтении (те же доводы, что в [view-panel.md §2.1](view-panel.md)).
- Расширение = новый файл `views/<mode>.py` + одна строка в `MODE_VIEWS` + строка подписи в `display` (D8). `tab.py`, `window.py`, панель — не трогаются.

Альтернатива «`Gtk.Stack` с тремя заранее созданными виджетами и `if`-переключением» отвергнута: она прячет раскладку каждого режима в одном файле и не даёт каждому режиму иметь своё состояние (скролл, ширина колонок).

### D2. Общий контракт `ListingView` и общая модель элемента

Сейчас `Row` (GObject) живёт внутри `views/details.py` и по смыслу общий: имя, путь, размер, дата, тип. Он переезжает в `views/item.py` как `ListingItem` и становится общей моделью элемента для всех режимов.

```python
# src/volna/views/base.py
class ListingView(abc.ABC):
    """Одно представление листинга. Данные — одни; различается только раскладка."""

    mode: ClassVar[ViewMode]

    def __init__(self, *, on_activate: Callable[[ListingItem], None]) -> None: ...

    @property
    @abc.abstractmethod
    def widget(self) -> Gtk.Widget:
        """Корень виджета режима; вкладка кладёт его в свой стек."""

    @abc.abstractmethod
    def render(self, sections: Sequence[Section]) -> None:
        """Показать содержимое; заменяет всё предыдущее."""

    def apply(self, settings: ViewSettings) -> None:
        """Реакция режима на настройки (плотность). По умолчанию — ничего."""

    def reset_scroll(self) -> None:
        """Вернуть прокрутку в начало (вызывается при переключении режима)."""
```

Контракт маленький и общий для всех режимов — это и есть точка, где «расширение» становится дешёвым: новый режим реализует `widget`/`render`, а переключение, применение настроек и жизненный цикл остаются в диспетчере.

`ListingItem` остаётся `GObject` (нужен типизированному `Gio.ListStore`), но его поля — чистые данные: `name`, `path`, `is_dir`, `size_text`, `date_text`. Сборку `Entry → ListingItem` делает вкладка ([tab.py:181](../src/volna/tab.py)) — она единственная знает и про `core`, и про `views` (§3).

### D3. Секции — шов для будущей группировки

Контракт принимает не плоский список, а **последовательность секций**:

```python
@dataclass(frozen=True, slots=True)
class Section:
    """Часть листинга с необязательным заголовком (будущая группа по дате)."""

    header: str | None
    items: tuple[ListingItem, ...]
```

Сейчас секция всегда одна и безымянная (`header=None`); группировка (отложена, §12) превратит её в N именованных секций — **контракт видов не меняется**, меняется только то, что строит вкладка.

Почему секция уже сейчас, а не «потом переделаем»:

- Группировка — не гипотеза, а требование спеки ([01-product-direction §2](spec/01-product-direction.md), [04-components §6.2](spec/04-components.md)): все три режима имеют сгруппированный и несгруппированный варианты. Контракт `render(sections)` — это уже форма спеки, а не абстракция ради абстракции.
- Смена контракта позже = правка трёх модулей видов + вкладки. Сейчас это стоит один `dataclass` на 4 строки.
- Обратная совместимость: плоский случай — это просто секция без заголовка; ни один вид не обязан уметь рисовать заголовок, чтобы быть рабочим.

Правило для режима «Столбцы» (D5 ниже): **колонка = секция**; безымянная секция (плоский случай) режется на колонки фиксированного размера. Когда появится группировка, правило станет единым: секция = колонка. Это единственное «некрасивое» место контракта, и оно исчезает само.

### D4. Диспетчер режимов — в вкладке; активен ровно один вид

`DirectoryTab` владеет реестром представлений и переключает видимый. Никакого «режима» в `window.py`.

```python
# src/volna/tab.py (проект)
class DirectoryTab:
    def __init__(..., capabilities: ViewCapabilities = ...):
        self._views: dict[ViewMode, ListingView] = {
            mode: factory(on_activate=self._on_item_activated)
            for mode, factory in VIEWS_BY_MODE.items()
            if mode in capabilities.modes
        }
        self._stack = Gtk.Stack()
        for mode, view in self._views.items():
            self._stack.add_named(view.widget, mode.value)
        self.widget = self._stack
```

Свойства диспетчера:

1. **Ровно один активный вид.** Данные (`ListingItem`) строятся один раз и рисуются только активным видом: три режима на 100k записей — это три прохода по данным, а нужен один.
2. **Переключение режима — это изменение отображения, а не сканирование.** Модель не трогается: `generation` не меняется, `ScanState` остаётся `READY`, «Сканирование…» не мигает. Ровно та же семантика, что у сортировки и скрытых файлов ([view-panel.md §2.5](view-panel.md)).
3. **Прокрутка сбрасывается** при смене режима ([05-interactions §3](spec/05-interactions.md)): новый активный вид получает `reset_scroll()`.
4. **Уходящий вид очищается** (`render([])`): неактивный вид не держит 100k `ListingItem` в своём сторе.
5. **Порядок событий**: `update_view_settings(view_mode=…)` → merge + `normalized` → guard «ничего не изменилось → False» → переключение видимого ребёнка стека → перерисовка активного вида из модели (без I/O).

### D5. Раскладка каждого режима

Общие правила для «Столбцов» и «Значков» (из [04-components §6.2](spec/04-components.md)):

- Имя элемента — до двух строк; обрезка — `MIDDLE` (видны начало и хвост — расширение/версия), а не `END`; полное имя — в tooltip, когда имя реально обрезано. Переключатель «Показывать имена целиком» ([view-panel.md](view-panel.md)) отключает обрезку в «Столбцах» (колонка шириной контента) и «Значках» (ширина плитки ≤ 240 px, затем высота ≤ 4 строк); «Подробности» режут всегда по ширине колонки. Решение — D29 ([07-decisions](spec/07-decisions.md)). Метаданные (размер, дата) — моноширинным приглушённым.
- Папка — единственный насыщенный цветной глиф; файл — нейтральный контурный документ (тот же выбор, что в «Подробностях», [naming.py](../src/volna/naming.py)).
- Скрытые элементы в этом приложении **не показываются вовсе** (политика `show_hidden` в модели), а не показываются приглушёнными, как в макете. Расхождение осознанное и уже зафиксировано в [view-panel.md §2.5](view-panel.md).
- Плотность влияет на метрики ячеек: колонка 66 → 54 px, плитка 150 → 132 px.
- Активация: двойной клик открывает папку — сигнал `activate` у `GridView`/`ListView` даёт позицию элемента; для «Столбцов» позиция — это (колонка, строка), из неё вычисляется элемент. Обработчик тот же, что в «Подробностях» ([tab.py:147](../src/volna/tab.py)).
- Пустой листинг: сейчас приложение показывает просто пустую таблицу; в макете — сообщение по центру. Это общий элемент для всех режимов, а не часть новых, — в эту итерацию не входит, но режимы не должны этому мешать (пустой вид — пустой, без ошибок).

#### «Подробности» — без изменений

Остаётся `Gtk.ColumnView` с тремя колонками (Имя/Размер/Дата). Меняется только оболочка: `Row` → `ListingItem`, `DetailsView` наследует `ListingView`. Секции пока безымянные — таблица выглядит как сегодня.

#### «Значки» — сетка плиток

- Вертикальная прокрутка; сетка плиток; плитка: иконка (48 px, при зуме 48–72), имя (до 2 строк), размер и дата моноширинным приглушённым.
- Ширина плитки — 150 px (сетка `repeat(auto-fill, minmax(150px, 178px))` в макете), минимальная высота 150 px (плотная — 132).
- GTK: `Gtk.GridView` + `Gio.ListStore(ListingItem)` + `Gtk.SignalListItemFactory` — виртуализация GTK, как и в «Подробностях» (D25 в [07-decisions](spec/07-decisions.md)).
- **Замер (GTK 4.14.5, Xvfb):** `GtkGridView` сам считает число колонок как `floor((ширина − скроллбар) / минимальная ширина плитки)` и **растягивает плитки поровну** до заполнения ширины: при минимальной ширине 150 px в полосе 1200 px получилось 7 колонок по 171 px, в полосе 700 px — 4 колонки по 175 px. Оба значения попадают в диапазон макета (150–178 px), то есть `minmax(150px, 178px)` воспроизводится без ручного счёта.
- **Важно:** у `GtkGridView` по умолчанию `max-columns = 7` — он срезает сетку до семи колонок. Для нашего диапазона его надо поднять (`set_max_columns`), иначе в широкой полосе плитки станут шире задуманного.

#### «Столбцы» — горизонтальные колонки

- Безголовые колонки, горизонтальная прокрулка; элемент колонки: иконка 48 px + трёхстрочный текст (имя / размер / дата); ширина колонки — content-sized, минимум 190 px (в широком пресете 238–375 px, как в макете).
- Порядок обхода: сортировка, затем заполнение колонки сверху вниз (column-major) — [05-interactions §4](spec/05-interactions.md).
- **Колесо.** Любая ось колеса/тачпада листает колонки **по горизонтали**: листинг течёт слева направо, поэтому обычное вертикальное колесо и наклон/`Shift`+колесо двигают его по его собственной оси. Это делается `Gtk.EventControllerScroll` в **capture-фазе** (иначе встроенный обработчик `Gtk.ScrolledWindow` в bubble-фазе съедает событие), шаг — `px(100)` за щелчок, значение зажимается в диапазоне прокрутки. Следствие: вертикальная прокрутка колесом в этом режиме не работает — если 6 строк не влезают по высоте (очень низкое окно), до них добираются полосой прокрутки.
- GTK: внешний **горизонтальный** `Gtk.ListView` (свойство `orientation` у `GtkListBase`, доступно с GTK 4.0; модель — индексы колонок), фабрика строит колонку из ≤6 элементов. Колонка — это 6 элементов, то есть **вложенная виртуализация не нужна**: внешний список виртуализирует колонки, внутри колонки виджеты строятся напрямую.

**Замер (GTK 4.14.5, Xvfb, полоса 1200×700, 40 колонок по 6 элементов):**

| Что | Результат |
|---|---|
| Раскладка | колонки идут слева направо, порядок column-major сохранён (проверено на кадрах до и после прокрутки) |
| Высота элемента | **всю высоту полосы** (696 px при полосе 700) — по второстепенной оси элемент растягивается |
| Выравнивание | содержимое колонки **по верху** (y = 0), а не по центру |
| Ширина | content-sized (190 px), по ширине не растягивается |
| Прокрутка | горизонтальная работает (`hadjust`: page 1200, upper 7760 при 40 колонках); **вертикальной нет** (`vadjust`: upper == page) |
| Виртуализация | 2000 колонок в модели → **7 живых** в раскладке (205 bind-ов за всю сессию) |
| Колесо | реальные X11-события (XTest) сдвинули `hadjustment` 0 → 250 при 4 щелчках; `vadjustment` остался 0, хотя вертикаль переполнена (617 > 372) — встроенный обработчик обойдён |

То есть конструкция «колонка = список элементов» работает как задумано: полоса не прокручивается по вертикали, колонка растёт вправо, пустое место под короткой колонкой остаётся сверху.

**Замер подписи:** `Gtk.Label` с `lines=2` + `wrap` + `ellipsize=END` даёт ровно двухстрочный clamp с многоточием (высота 38 px против 19 px при `lines=1`) — эквивалент `line-clamp: 2` из макета.

**Открытое решение ОД-1 — сколько строк в колонке.** В макете — фиксированные 6 (`perColumn = 6`). Вариант «сколько влезает в высоту полосы» ближе к поведению настоящих файловых менеджеров и делает плотность осмысленной, но требует пересчёта при изменении размера окна.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Фиксированные 6** (как в макете) | совпадает с макетом и спекой; предсказуемо; нет зависимости от resize | в высоком окне под колонкой пустота; плотность на число строк не влияет |
| **B. По высоте полосы** | колонка заполняет окно; плотность влияет на число строк | пересчёт при resize; расходится с макетом |

Рекомендация — **B**: в реальном окне (1800×1125, широкий пресет) полоса контента ≈ 730 реальных px, а 6 строк по 82 px занимают 496 — треть полосы пустая. По высоте полосы получится ≈ 8 строк (плотная раскладка — ≈ 10). Правило изолировано в модуле режима, поэтому пересчёт при resize — локальная правка, а не переделка.

### D6. Честные capabilities: что эта сборка умеет

`ViewCapabilities.modes` — единственный источник правды о том, какие режимы вообще есть. Панель строит список радио из `capabilities.modes` (D8), вкладка создаёт только доступные представления, `normalized()` приводит сохранённый недоступный режим к `preferred_mode()` — этот путь уже написан и протестирован.

**Проверять версию GTK для режимов не нужно.** Горизонтальный `Gtk.ListView`/`Gtk.GridView` (свойство `GtkListBase:orientation`) и `GtkGridView:min-columns/max-columns` существуют **с GTK 4.0** — проверено по исходникам 4.0.0 (`gtk/gtklistbase.c`: `GtkOrientable` + `PROP_ORIENTATION`; `gtk/gtklistview.c` и `gtk/gtkgridview.c` учитывают `orientation`). Значит «Столбцы» не поднимает требование к GTK: текущий минимум приложения остаётся «GTK 4».

Проверка версии понадобится, если появится режим, которому нужен более новый API (например, заголовки групп через `Gtk.ListView:header-factory` — GTK 4.12). Тогда гейт делается в composition root (`main.py`), где GTK доступен: `display` не импортирует GTK по правилу слоёв, а `MainWindow` уже принимает `capabilities` — меняется только то, кто их собирает.

```python
# main.py (проект)
def _capabilities() -> ViewCapabilities:
    """Что эта сборка умеет."""
    return ViewCapabilities(
        modes=frozenset({ViewMode.DETAILS, ViewMode.COLUMNS, ViewMode.ICONS}),
        grouping=False,
        density=True,
        zoom_modes=frozenset(),
    )
```


### D7. Переключатель — только в панели «Вид»

Одна настройка — один контрол ([07-decisions D05](spec/07-decisions.md)): новая фича-настройка `view_panel/settings/view_mode.py` по образцу `sort_key.py`.

- Секция «Режим просмотра», радио-группа: «Значки» / «Столбцы» / «Подробности» (порядок и формулировки — как в макете).
- `available(capabilities)` → `False`, если доступен только один режим: секция не рендерится вовсе.
- Строки строятся **из `capabilities.modes`**, а не из захардкоженного списка: недоступный режим не показывается, а появление нового режима не требует правок панели.
- Порядок секций в поповере: «Режим просмотра» → «Сортировка» → «Параметры» (секции группируются по первому появлению в реестре `SETTING_FEATURES`, [view_panel/panel.py:149](../src/volna/view_panel/panel.py) — достаточно поставить новую фичу первой в кортеж).

Иконка триггера «Вид» остаётся статичной (`columns`, как в макете): триггер открывает настройки, а не показывает текущий режим.

### D8. Данные, а не код: подписи и порядок режимов живут в `display`

Радио-строки панели строятся из данных, а не из литералов в UI-коде ([AGENTS R-DATA](../AGENTS.md)):

```python
# display/settings.py (проект)
class ViewMode(StrEnum):
    DETAILS = "details"
    COLUMNS = "columns"
    ICONS = "icons"

    @property
    def label(self) -> str:
        return _MODE_LABELS[self]

MODE_ORDER: tuple[ViewMode, ...] = (ViewMode.ICONS, ViewMode.COLUMNS, ViewMode.DETAILS)
```

Порядок в панели — по `MODE_ORDER` (порядок макета), а не по порядку enum: enum отражает алфавит/историю, панель — продуктовое решение.

| Что | Класс |
|---|---|
| плитка «Значков» | `volna-icons-tile`, `volna-icons-name`, `volna-icons-meta` |
| колонка «Столбцов» | `volna-col`, `volna-col-item`, `volna-col-name`, `volna-col-meta` |

### D10. Иконки остаются своими; иконки типов файлов — отдельная фича

Сейчас у любого файла один нейтральный глиф ([naming.py](../src/volna/naming.py)), у папки — свой двухтоновый. Токены дизайна требуют единый стиль: контурные глифы, `currentColor`, «все иконки — inline SVG, без внешних спрайтов», а папка — «единственный насыщенный цветной глиф» ([02-design-tokens §6](spec/02-design-tokens.md)).

Взять иконки из системной темы технически можно: `Gio.content_type_guess(name, None)` (угадывание типа по имени, без чтения файла) → `Gio.content_type_get_icon()` → `Gio.ThemedIcon` → `Gtk.Image.set_from_gicon()`. Но это меняет дизайн и добавляет зависимость от окружения:

- вид иконки зависит от темы пользователя и от наличия `shared-mime-info` → рендер перестаёт быть детерминированным, пиксельные пробы и визуальные сверки теряют смысл ([AGENTS R-CONTROL](../AGENTS.md): на то, что мы не контролируем, полагаться нельзя);
- темы ограничены набором размеров: 48–72 px придётся брать из соседнего, а растровые темы растянутся и станут мыльными;
- правило «папка — единственный насыщенный цветной глиф» ломается: иконки типов в Breeze/Adwaita цветные.

Решение: **свои SVG остаются** (хром, папка, нейтральный файл). Иконки по типу файла — отдельная фича («иконки типов») со своим решением по теме и явной политикой фолбэка; в итерацию режимов не входит. В этой итерации новых размеров глифов нужно два: 40 и 48 px в базовой сетке (плюс 60/72 px при зуме) — SVG векторные (`viewBox 0 0 16 16`), новый вариант = копия с другим `width`/`height`.

## 3. Слои и зависимости

```
main.py / window.py  — composition root: capabilities (с учётом версии GTK), панель, вкладки
   ▼
tab.py               — диспетчер режимов: представления, стек, переключение, сборка элементов
   │ ListingItem, Section, ListingView
   ▼
views/               — GTK-рендереры: registry + по модулю на режим
   │
   ▼
display              — ViewMode, ViewSettings, ViewCapabilities (без GTK)
   │
   ▼
core                 — DirModel: данные, порядок, видимость (без GTK)
```

Правила (те же, что в [view-panel.md §3](view-panel.md), плюс новые):

1. `core` не знает о режимах: режим — политика отображения, а не данные.
2. `display` не импортирует GTK; `views` импортирует `display`, но не `view_panel` и не `core`.
3. `views` — единственное место, где режимы реализованы; каждый режим — отдельный модуль, общий контракт в `views/base.py`.
4. `tab.py` — единственное место, где выбирается активный вид; `window.py`/`main.py` знают всех, но не выбирают режим за вкладку.

Проверка правил — тест на импорты (как в [view-panel.md §7.1](view-panel.md)).

Внутреннее (проект, не публичный API):

## 5. Поток данных при смене режима

```
клик «Столбцы» в поповере
  → ViewModeSetting._emit(view_mode=ViewMode.COLUMNS)
  → panel._on_change → window._update_view_settings(view_mode=COLUMNS)
  → tab.update_view_settings(view_mode=COLUMNS)
        settings = current.merged(capabilities, view_mode=COLUMNS)
        guard: settings == current → False (ничего не делаем)
        self._settings = settings
        _activate_view(COLUMNS):  stack.set_visible_child("columns")
                                previous_view.render([])   # освободить стор
                                new_view.reset_scroll()
        model.set_order/set_folders_first/set_show_hidden  # без изменений → False
        _schedule_refresh()   # один idle-тик
  → _refresh: items = [ListingItem(e) for e in model.entries()]
               sections = [Section(header=None, items=tuple(items))]
               active_view.render(sections)
  → panel.sync() — радио «Столбцы» отмечен
```

Инварианты:

- `model.generation` не меняется, `ScanState` остаётся `READY`, I/O нет.
- Один клик → максимум одна перерисовка (idle-refresh коалессирует).
- Изменение касается только активной вкладки; вторая вкладка сохраняет свой режим; новая вкладка наследует снимок активной (наследование уже реализовано в [window.py:1030](../src/volna/window.py)).
- Активен ровно один вид; данные строятся один раз на перерисовку.

## 6. Хранилище

Схема не меняется: `view_mode` уже в `view` ([display/settings.py:92](../src/volna/display/settings.py)), `schema_version` остаётся 1, `from_mapping` уже умеет откатывать неизвестный enum в дефолт, `normalized()` — приводить недоступный режим к `preferred_mode()`.

Следствия:

- Режим переживает перезапуск: закрыли окно → `store.save(view активной вкладки)` → следующий запуск открывает приложение в том же режиме.
- Сохранённый режим, которого нет в `capabilities` этой сборки → `normalized()` → `preferred_mode()` — тихий и предсказуемый откат.
- Файл, сохранённый старой версией приложения, читается как есть: неизвестные поля игнорируются, новых полей нет.

## 7. Тесты

Принцип — [AGENTS R-SYSTESTS](../AGENTS.md): системные тесты независимы от реализации.

### 7.1 Без дисплея (юнит)

- реестр `MODE_VIEWS` покрывает все `ViewMode`; у каждого класса уникальный `mode`; `VIEWS_BY_MODE` согласован с кортежем;
- `ViewMode.label` и `MODE_ORDER` — данные, а не разбросанные литералы;
- `ListingItem`: сборка из `Entry` (размер каталога — «—», дата — формат `views/format.py`);
- `Section`: безымянная секция плоского листинга;
- `ViewSettings.normalized()`: недоступный режим → `preferred_mode()` (для режима, которого нет в capabilities);
- импортные правила: `display` не тянет GTK/`views`; `views` не тянет `core`/`view_panel`.

### 7.2 Виджеты (Xvfb)

- в панели появляется секция «Режим просмотра» с тремя радио; при одной доступном режиме секции нет;
- выбор радио переключает видимый вид в **активной** вкладке и не трогает вторую;
- переключение режима **не запускает скан**: `generation` и `ScanState` не меняются;
- после переключения видно те же элементы, что и до (те же имена), порядок сохранён;
- новая вкладка наследует режим активной;
- переключение режима сбрасывает прокрутку;
- недоступный режим не рендерится (сборка с `capabilities.modes = {DETAILS}` → панель без секции, вкладка без лишних виджетов).

### 7.3 Системные (независимы от реализации)

- в каталоге с реальными файлами: «Подробности» → таблица; переключение в «Значки» → те же имена плитками; в «Столбцы» → те же имена по колонкам, порядок column-major (проверка по позициям виджетов, не по внутреннему состоянию);
- режим переживает перезапуск (тот же `XDG_CONFIG_HOME`);
- переключение режима не показывает «Сканирование…» и не меняет счётчики.

### 7.4 Нефункциональные (`slow`)

- 100k записей: переключение режима и перерисовка не блокируют UI дольше ~200 мс; память не растёт от трёх видов сразу (неактивный вид очищен).

[grouping.md](grouping.md).** Вкладка строит N именованных секций из `model.groups()`; каждый вид рисует заголовок («Сегодня» + счётчик); в панели — секция «Группировка» (радио «По дате изменения» / «Без группировки»), `capabilities.grouping = True`. Ядру менять сортировку не пришлось: глобальная сортировка + раскладка по корзинам уже даёт порядок **внутри** группы ([05-interactions §5](spec/05-interactions.md)), группы идут в порядке корзин.
2. **Масштаб (zoom).** Слайдер в панели; `zoom_modes` в возможностях; ширина колонки и размер иконки плитки — по формулам макета ([05-interactions §6](spec/05-interactions.md)). Поле `zoom` в настройках уже есть.
3. **Пресеты.** Схема v2 (`presets`, `active`), применение пресета пишет снимок в активную вкладку — [view-panel.md §10.1](view-panel.md).
4. **Выделение и инспектор.** Режимы получают общий контракт выделения; «Сведения» в правой панели.
5. **Четвёртый режим** (например, «Список»): новый модуль `views/<mode>.py` + строка в `MODE_VIEWS` + подпись в `display`. Больше ничего.
6. **Минимальная версия GTK.** Для режимов поднимать пол не нужно: горизонтальные списки и `GridView:min/max-columns` есть с GTK 4.0 (D6). Группировка тоже не подняла пол: заголовки групп сделаны на `ListView`/`ColumnView` с гетерогенными строками, а не на section-API GTK 4.12 (grouping.md D5–D6). Если когда-нибудь понадобится `Gtk.ListView:header-factory` — пол **4.12**, а не 4.10: 4.10 не даёт ничего нужного, а 4.12 даёт. Практическая цена пола 4.12: Debian 12 (GTK 4.8) и Ubuntu 22.04 (GTK 4.6) выпадают; Debian 13 (4.18), Ubuntu 24.04 (4.14), Fedora 40+ (4.14+), Arch/Tumbleweed — проходят. Отдельно: `PyGObject` должен быть не старше, чем требует выбранный GTK.
