# «Панель вида» — проект и реализация (V1, согласованный скоуп)

**Статус:** V1 реализован и проверен (2026-11-16). Основание: спецификация [design/spec](spec/README.md) v1.5, канонический макет [`design/artifacts/variant-c.html`](artifacts/variant-c.html), состояние кода `HEAD 425227a`.
**Предмет:** поповер «Вид» (тулбарный триггер + сортировка + скрытые + плотность) с настройками **на вкладку** и сохранением последнего вида.
**Не предмет (эта итерация):** пресеты, группировка, режимы «Значки»/«Столбцы», масштаб, фильтр по имени, инспектор, настройка размера интерфейса. Их проект — в §10.

Решения по скоупу зафиксированы с владельцем продукта 2026-11-15:

| Вопрос | Решение |
|---|---|
| Скоуп V1 | только UI панели: триггер + поповер + сортировка/скрытые/плотность; без пресетов |
| Последний вид | **сохранять** между запусками |
| Скрытые файлы | по умолчанию **скрыты** |
| Область настроек | **свои у каждой вкладки** |

Следствия, которые в этом документе разворачиваются: хранилище остаётся, но в нём живёт только **активный вид** (не пресеты); панель управляет **активной вкладкой**; новые вкладки **наследуют** снимок активной; секции «Пресеты», «Группировка», «Режим просмотра», «Масштаб» в V1 отсутствуют.

---

## 1. Что строим

| Область | Содержание |
|---|---|
| Триггер и поповер | «Вид» в тулбаре (слева от пути); поповер с секциями «Сортировка» и «Параметры», клавиатура, фокус, закрытие |
| Настройки | `ViewSettings` — неизменяемый снапшот из 8 полей; в V1 действуют 5: ключ и направление сортировки, «папки перед файлами», скрытые, плотность |
| Владение | настройки принадлежат вкладке; панель читает/меняет активную вкладку; новая вкладка наследует снимок |
| Хранение | JSON в XDG config: **последний вид** активной вкладки на момент выхода; атомарная запись, деградация без падения |
| Поведение | сортировка/скрытые/плотность без рескана и без фейкового «Сканирование…»; dotfiles скрыты по умолчанию |
| Качество | системные тесты (UI и перезапуск), юнит-тесты домена и хранилища, доступность нативных контролов |

### 1.1 Чего в панели не будет и почему

- **Пресеты** — отложены (см. §10.1). Панель V1 не содержит секцию «Пресеты» и диалоги.
- **Группировка** — отложена вместе с заголовками групп (§10.2).
- **Режим просмотра и масштаб** — нет целевых режимов; секции не рендерятся, чтобы не было мёртвых контролов (§2.4).
- **Фильтр по имени** — отдельная фича тулбара редактора.
- **QA deep-links** (`#view` и т. п.) — механика макета, в продукте не нужна.

## 2. Ключевые решения

### 2.1 Решение 1. Панель — обычный модуль; «фичи» — это отдельные настройки

`view_panel` — такой же модуль приложения, как `views/` или `display/`: это **не** feature и **не** plugin, у него нет реестра фич, lifecycle и динамического обнаружения. Feature-подход применяется только к **настройкам внутри панели**: каждая настройка — отдельный модуль/класс (решение 2.10), состав задаётся явным кортежем.

Почему так:

- Панель — обязательная часть окна, а не сменяемое расширение; «фича-обёртка» вокруг неё ничего не даёт, но добавляет слой композиции и терминологическую путаницу.
- Реестр фич/entry points добавил бы скрытую композицию, зависимость от факта установки пакета и порядок загрузки — против [AGENTS §12, §17, §23](../AGENTS.md); для настроек достаточно явного кортежа `SETTING_FEATURES`.
- Настройки действительно выигрывают от отдельных модулей: панель не знает полей и контролов, добавление настройки — новый файл + строка реестра.

**Триггер пересмотра:** панель должна включаться/выключаться без пересборки или появляются внешние расширения — тогда (и только тогда) обсуждать feature/plugin-обёртку.

### 2.2 Решение 2. Домен отдельно от UI-панели

```
core/    (чистые данные листинга)  ← display/ (чистые ViewSettings, возможности, хранилище)
views/   (GTK-рендер листинга)     ← view_panel/ (GTK-триггер и поповер, обычный модуль)
window.py / main.py                — composition root: собирают всё явно
```

- `display/` не импортирует GTK и не читает окружение неявно: пути/store передаются снаружи.
- `view_panel/` не содержит политики: контролы вызывают колбэки окна и показывают состояние.
- `views/details.py` не знает про панель; получает примитивы/типы домена.
- Никаких глобальных синглтонов; `display/__init__.py` ре-экспортирует `SortKey` из core, чтобы модуль панели не импортировал core напрямую.

### 2.3 Решение 3. Настройки — на вкладку; панель правит активную

- Каждая `DirectoryTab` владеет своим `ViewSettings`: это единственный источник истины для своей таблицы. Панель не хранит состояние — она читает снимок активной вкладки при открытии и после каждого изменения.
- Изменение из панели идёт в активную вкладку: `tab.update_view_settings(**changes)` → merge + `normalized(capabilities)` → guard «без изменений → False» → применить к модели/виду → перерисовать.
- **Новая вкладка наследует** снимок активной на момент создания (вкладки не восстанавливаются после перезапуска, поэтому отдельного «вида вкладки» в хранилище нет).
- **Плотность** — свойство активной вкладки; класс `volna-density-compact` висит на окне и отражает плотность активной вкладки (при переключении переключается).
- Пресеты (когда появятся) будут глобальными снапшотами: их применение запишет снимок в активную вкладку.

### 2.4 Решение 4. UI честный: секции зависят от возможностей

`ViewCapabilities` — данные о том, что приложение реально умеет: какие режимы, есть ли группировка/плотность/масштаб. Панель рендерит только применимые секции, настройки нормализуются к возможностям при загрузке и merge.

V1: `ViewCapabilities(modes={DETAILS}, grouping=False, density=True, zoom_modes=∅)`. Следствие: в поповере только «Сортировка» и «Параметры» + footer. `view_mode`, `grouping`, `zoom` живут в модели и в схеме хранения (forward-compatible), но UI и эффекта у них пока нет.

Почему не показываем неактивные опции: мёртвый контрол — ложь UI ([AGENTS §19, §17](../AGENTS.md)).

### 2.5 Решение 5. Сортировка и скрытые — без рескана

- Сортировка: `DirModel.set_order(key, reverse)` пересортировывает уже загруженный список, эмитит `ORDER_CHANGED`; вкладка перерисовывается существующим idle-refresh. I/O нет, статус остаётся `READY`.
- Скрытые: сканер по-прежнему перечисляет всё; `Entry.is_hidden` (по имени), `DirModel.show_hidden` фильтрует выдачу, `entries()`/`counters()` считают **видимые** записи. Переключение — без I/O и без `SCANNING`.
- Следствие: dotfiles впервые скрыты по умолчанию (сейчас приложение показывает их всегда) — в релиз-ноту и системный тест.
- Счётчики видимых: либо два счётчика, либо пересчёт по списку при переключении (O(n), замер в slow-тесте); в любом случае тулбар показывает то, что видно в таблице.

### 2.6 Решение 6. Хранение — версионированный JSON «последнего вида»

`$XDG_CONFIG_HOME/volna/settings.json` (fallback `~/.config/volna/settings.json`), `schema_version: 1`, поле `view` (8 полей; новые поля добавляются без смены версии — старый файл читается с дефолтами). Атомарная запись, никаких исключений наружу, деградация в память. GSettings отклонён: схема требует установки/компиляции, dconf зависит от session bus, атомарность и миграции не под нашим контролем.

Записываем **снимок активной вкладки на момент закрытия окна/выхода**. Изменения в течение сессии живут в памяти — не пишем на каждый клик. Аварийное завершение теряет последний вид (допустимо; пресетов, которые можно потерять, в V1 нет).

### 2.7 Решение 7. Никаких фейковых статусов

Применение настроек не запускает скан и не мигает «Сканирование…»; статус-бар показывает реальный `ScanState`. Обратной связи «сохранено» в V1 нет (пресетов нет); ошибка сохранения последнего вида при выходе — одна заметка/лог, приложение закрывается штатно.

### 2.8 Решение 8. Имена CSS-классов

- Триггер: `Gtk.MenuButton` с классами `volna-view-trigger volna-menu-button`; внутри — существующий `volna-view`-бокс без изменений.
- Поповер: `volna-view-popover` (не вешаем `volna-menu`: у меню свой padding/минимальная ширина).
- Плотность: `volna-density-compact` на окне (не `is-compact` — «компактный» занят будущим размером интерфейса).
- Состояния — `is-current`/`is-active`, как в существующем коде.

### 2.9 Решение 9. «Папки перед файлами» — настройка сортировки

Поведение ядра «сначала папки» стало явной настройкой `folders_first`, а не жёстким правилом: по умолчанию она **включена** и сохраняет прежний вид, выключение смешивает папки и файлы в общем порядке выбранного ключа (при отсутствии значения — например, размера у каталога — элемент уходит в конец, как и раньше).

Механизм: `sort_entries(..., folders_first=bool)` в [core/order.py](../src/volna/core/order.py), `DirModel.folders_first` + `set_folders_first()` (re-sort в памяти, `ORDER_CHANGED`, без рескана) и поле в `ViewSettings`. UI — отдельная фича-настройка `view_panel/settings/folders_first.py` (чекбокс в секции «Параметры»), добавленная в реестр без правок панели — это и проверка декомпозиции на практике.

Отличие от макета: спека такого контрола не содержит; это продуктовое расширение по запросу, дефолт совместим с прежним поведением.

### 2.10 Решение 10. Каждая настройка — отдельная фича-модуль

Настройка в панели — это не ветка в `panel.py`, а самостоятельный класс в своём модуле `view_panel/settings/<setting>.py`. Он владеет **только своим контролом и своим полем** `ViewSettings`:

- `id` и `section` — куда и под каким заголовком встаёт строка;
- `available(capabilities)` — показывать ли её в текущей сборке;
- `widget()` — построить контрол из универсальных примитивов (`controls.py`);
- `sync(settings)` — отразить снимок без обратного «пользовательского» события;
- `_emit(**changes)` — сообщить панели **декларативный** дифф полей.

Панель не знает ни `SortKey`, ни имён полей: она группирует зарегистрированные фичи по `section`, строит секции и передаёт диффы в единый `update(**changes)`. Реестр `SETTING_FEATURES` — явный кортеж в `settings/__init__.py` (без importlib/entry points), поэтому состав панели виден в одном месте и не зависит от факта установки пакета.

Граница ответственности: **применение** изменений остаётся в одном механизме (`DirectoryTab.update_view_settings` → `model.set_order`/`set_show_hidden`/класс плотности), а не размазывается по фичам. Фича настройки не импортирует `tab`/`model`/`window` — только `display`-типы и примитивы контролов; это и снижает связность.

Цена: на настройку появляется небольшой модуль (~40 строк) и строка в реестре. Добавление настройки больше не требует правок панели; для нового **поля** всё равно нужны `ViewSettings` + эффект в вкладке (это честная граница данных и механизма).

## 3. Слои и зависимости

```
main.py / window.py  — composition root
   │ загрузка последнего вида; создание панели; вкладки получают/наследуют снимок
   ▼
view_panel           — GTK: триггер, поповер, секции; колбэки в окно
   │ ViewSettings / SortKey (ре-экспорт)
   ▼
display              — чистый домен: ViewSettings, ViewCapabilities, paths, store
   │ SortKey
   ▼
core                 — Entry, order, model, scanner (без GTK)
```

Правила:

1. `core` не импортирует `display`, `views`, `view_panel`.
2. `display` не импортирует GTK, `views`, `view_panel`; знает только `core` и stdlib.
3. `views` может импортировать типы `display` (`ViewSettings`), но не `view_panel`.
4. `view_panel` импортирует `display` и GTK; не импортирует `core`/`views` напрямую и не знает про `tab.py`.
5. `window.py`/`main.py` знают всех; это единственное место склейки.

Проверка правил 1–4 — тест на импорты (см. §7).

### 4.1 Домен: настройки

```python
# display/settings.py
class ViewMode(StrEnum):
    DETAILS = "details"     # пока единственный реальный
    ICONS = "icons"
    COLUMNS = "columns"

class Grouping(StrEnum):
    DATE = "date"
    NONE = "none"

@dataclass(frozen=True, slots=True)
class ViewCapabilities:
    modes: frozenset[ViewMode]
    grouping: bool
    density: bool
    zoom_modes: frozenset[ViewMode]

V1_CAPABILITIES = ViewCapabilities(
    modes=frozenset({ViewMode.DETAILS}), grouping=False, density=True,
    zoom_modes=frozenset(),
)

@dataclass(frozen=True, slots=True)
class ViewSettings:
    view_mode: ViewMode = ViewMode.DETAILS
    grouping: Grouping = Grouping.DATE
    sort_key: SortKey = SortKey.MTIME      # core.order.SortKey, не дублируем enum
    reverse: bool = True                   # True = по убыванию (mtime desc)
    folders_first: bool = True             # по умолчанию сохраняет прежнее поведение
    show_hidden: bool = False
    compact: bool = False
    zoom: int = 50                         # 0..100, 50 = 100 %

    def normalized(self, caps: ViewCapabilities) -> ViewSettings: ...
    def merged(self, caps: ViewCapabilities, **changes: object) -> ViewSettings: ...
    def to_mapping(self) -> dict[str, object]: ...
    @classmethod
    def from_mapping(cls, raw: Mapping[str, object]) -> ViewSettings: ...  # не бросает
```

Правила: `zoom` округляется/зажимается 0..100; неизвестные enum → дефолт; неизвестные ключи игнорируются; `normalized()` приводит недоступный режим к первому доступному, группировку — к `NONE`, если недоступна; `merged()` = `replace(**changes).normalized(caps)`. `from_mapping` не мигрирует схему.

### 4.3 UI-панель

```python
# view_panel/panel.py
class ViewPanel:
    def __init__(
        self,
        *,
        settings: Callable[[], ViewSettings],          # снимок активной вкладки
        update: Callable[..., bool],                   # update(**changes) → применено?
        capabilities: ViewCapabilities,
        setting_features: Sequence[type[SettingFeature]] | None = None,
    ) -> None: ...
    def trigger(self) -> Gtk.MenuButton: ...           # MenuButton «Вид»
    @property
    def popover(self) -> Gtk.Popover: ...              # тестовый хэндл
    def open(self) -> None: ...                        # программно открыть (тесты/QA)
    def sync(self) -> None: ...                        # перечитать снимок (показ/смена активной вкладки)
    def close(self) -> None: ...                       # popdown
```

`ViewPanel` создаётся окном напрямую (обычный модуль, без фабрики-обёртки). Панель не владеет состоянием и не подписывается на модели: единственные входы — колбэки окна. `sync()` вызывается при `popover.show`, после `update(...)` и при смене активной вкладки, пока поповер открыт. `setting_features` — параметр для тестов и будущих композиций; приложение не передаёт его и получает реестр по умолчанию.

### 4.4 Вкладка и окно

```python
# tab.py
class DirectoryTab:
    def __init__(..., view_settings: ViewSettings): ...
    @property
    def view_settings(self) -> ViewSettings: ...
    def update_view_settings(self, **changes: object) -> bool: ...
    # merge+normalized+guard; set_order/set_show_hidden; view.apply; _schedule_refresh

# window.py
def _current_view_settings(self) -> ViewSettings: ...       # снимок активной вкладки
def _update_view_settings(self, **changes) -> bool: ...     # вкладка + класс плотности
def _apply_density(self, compact: bool) -> None: ...
def _save_view_settings(self) -> None: ...                  # store.save(active.view_settings)
```

`MainWindow(*, start_path, initial_settings: ViewSettings, settings_store: ViewSettingsStore, startup_issues=())` — снимок, хранилище и диагностику чтения загружает/создаёт приложение; первый таб создаётся с `initial_settings`. Новый таб — с `active_tab.view_settings` (или `initial_settings`, если вкладок ещё нет). `DirectoryTab` получает `capabilities: ViewCapabilities` (по умолчанию `V1_CAPABILITIES`) — чтобы нормализация была в одном месте. `startup_issues` показываются одной заметкой в статусе при первом переходе вкладки в `READY`, чтобы их не затёрло «Сканирование…».

## 5. Хранение

### 5.1 Путь и схема

`SettingsPaths.default(environ)` → `$XDG_CONFIG_HOME/volna/settings.json`, иначе `~/.config/volna/settings.json`; `None`, если нет ни XDG, ни HOME → `MemoryViewSettingsStore`.

- В файле — только `view` и `schema_version`; будущие поля (`presets`, per-directory и т. п.) добавляются в схему без ломки: неизвестные ключи игнорируются.
- `schema_version > 1`: файл читаем в режиме «только чтение» — дефолты, файл не перезаписываем.

### 5.2 Атомарная запись

`mkstemp` в каталоге настроек (`0600`, каталог `0700`) → `write` → `flush` → `fsync` → `os.replace` → best-effort `fsync` каталога. Никогда не `open(path, "w")`: при сбое/заполненном диске остаётся валидный старый файл. Сравнение с последним успешно записанным payload — идемпотентность. Никакого `pickle`/`eval`.

### 5.3 Когда пишем

| Событие | Запись |
|---|---|
| любое изменение настроек в сессии | только в памяти |
| закрытие окна / выход из приложения | `store.save(view активной вкладки)` |
| старт без файла | ничего; файл появится при первом закрытии |

При нескольких окнах в одном процессе: оба стартуют со снимком, загруженным при старте приложения, и каждое пишет свой при закрытии — last-writer-wins, приемлемо для V1 (см. §8).

### 5.4 Поведение при сбоях

| Ситуация | Поведение |
|---|---|
| файла нет | дефолты + `default`; каталог создаётся при первой записи |
| нет HOME/XDG, каталог недоступен | memory-store: приложение стартует, вид живёт в сессии, однократная заметка «Настройки не сохраняются» |
| битый JSON/не UTF-8/не объект | дефолты, лог `WARNING`, файл не трогаем; при следующей записи сохраняем как `settings.json.invalid-<ts>` |
| битое поле/неизвестный enum | поле → дефолт, остальные сохраняются |
| `schema_version > 1` | read-only дефолты, файл не перезаписываем |
| ошибка записи (read-only, ENOSPC) | вид работает в сессии; лог + однократная заметка при выходе; приложение закрывается штатно |
| два окна | каждое пишет свой снимок (last-writer-wins) |

Старт **никогда** не падает из-за настроек ([AGENTS §14, §32](../AGENTS.md)); чтение/запись/`Path.home()` — за guard'ами, прочие исключения не глушим.

## 6. Распространение изменений

### 6.1 Цепочка

```
клик по контролу в поповере
  → panel: update(sort_key=SortKey.NAME)                  [один вызов]
  → window._on_view_change:
        tab = self._active_tab (если нет — False)
        tab.update_view_settings(**changes)
  → DirectoryTab.update_view_settings:
        settings = current.merged(caps, **changes)
        guard «settings == current → False, ничего не делаем»
        self._settings = settings
        model.set_folders_first(...)  # re-sort в памяти + ORDER_CHANGED
        model.set_order(...)          # re-sort в памяти + ORDER_CHANGED
        model.set_show_hidden(...)    # фильтр + событие счётчиков
        view.apply(settings)          # плотность (в V1)
        _schedule_refresh()           # один idle-тик
  → panel.sync() после успешного update
  → window: класс volna-density-compact по активной вкладке
```

Инварианты:

- Изменение касается **только активной вкладки**; остальные не трогаются и не перерисовываются (это и есть выбранная per-tab семантика).
- Один клик → максимум одна перерисовка активной вкладки (idle-refresh коалессирует).
- `model.generation` не меняется, `ScanState` остаётся `READY`, `DirectoryController` не трогается.
- Панель всегда показывает снимок активной вкладки: `sync()` при показе, после update и при смене активной вкладки с открытым поповером (смена вкладки мышью закрывает поповер автоматически; клавиатурные пути — синхронизируются).

### 6.2 Что делает каждый контрол

| Настройка | Модель/вид | I/O | Перерисовка | Особенности |
|---|---|---|---|---|
| ключ сортировки | `model.set_order()` → re-sort | нет | idle | `None`/`—` в конце |
| папки перед файлами | `model.set_folders_first()` → re-sort | нет | idle | по умолчанию включено; выключение смешивает типы в общем порядке |
| направление | `model.set_order()` | нет | idle | UI `desc/asc` ↔ `reverse=True/False` |
| скрытые файлы | `model.set_show_hidden()` | нет | idle | счётчики по видимым; выделения пока нет |
| плотность | `view.apply()` + класс окна | нет | CSS | класс отражает активную вкладку |
| смена активной вкладки | — | нет | — | если поповер открыт — `panel.sync()`; класс плотности обновляется |

### 6.3 Ошибки и отказы

- Невалидное значение из UI не применяется (сначала merge + `normalized`, потом коммит).
- Исключение в `update_view_settings`/`render` не глушим — это баг; границы внешней среды (файлы, HOME) — только в store/paths.
- Ошибка сохранения при выходе: `WARNING` в лог, окно закрывается штатно; вид в следующей сессии начальный (файл остался прежним). Заметку в статусе при закрытии пользователь всё равно не увидит.

### 6.4 Триггер, поповер и геометрия

- **Триггер** — `Gtk.MenuButton` (`volna-view-trigger volna-menu-button`), внутри прежний `volna-view`-бокс: иконка `columns`, «Вид», шеврон `down`, высота `px(28)`. Слева от пути, не смещается при длине пути. Клик/`Space` открывают, `Escape` и клик вне закрывают, `active` синхронизируется. Тултип снимается на `show` и возвращается на `closed` (как у главного меню). `open()` — программный вход для тестов/QA.
- **Содержимое** — секции «Сортировка» (радио «Дата изменения»/«Размер»/«Имя», сегмент «По убыванию»/«По возрастанию», чекбокс «Папки перед файлами») и «Параметры» (чекбокс «Показывать скрытые файлы»; «Плотная раскладка» — только при `capabilities.density`), между ними 1 px линии, снизу footer «Изменения применяются сразу». Пресетов/группировки/режима/масштаба нет — мёртвых контролов не показываем.
- **Ширина и позиция**: `size_request` = `px(320)` — это ширина *контента* (400 px в широком пресете); GTK добавляет прозрачные поля под тень (surface ≈ на 12 px шире при тени `0 2px 4px`). Выравнивание по левому краю триггера задаёт сам GTK: `popover.set_halign(Gtk.Align.START)` (иначе поповер центрируется по триггеру), зазор 4 px — постоянный `offset = (0, 4)`. **Геометрия задаётся до первого показа и больше не меняется:** GTK позиционирует поповер в момент представления, поэтому коррекция в обработчике `show` (в т. ч. через `idle_add`) сдвигает уже открытую панель — это и есть «мигание». Измерено на реальном окне: контент 400 px, `content_left − trigger_left = 0`, зазор 4 px, поверхность поповера начинается по нижней границе триггера.
- **Тень и клики**: GTK строит поверхность поповера *вокруг* тени — размытие становится прозрачными полями поверхности, и они перехватывают клики по триггеру (панель «съедала» каждый второй клик: открыть → закрыть → пусто → открыть). Поэтому размытие тени панели ограничено зазором в 4 px (`0 2px 4px`): поверхность начинается по нижней границе триггера, и кнопка остаётся кликабельной целиком. Для панелей, привязанных к кнопке, тень должна быть меньше зазора.
- **Высота**: `Gtk.ScrolledWindow` внутри поповера, `max_content_height = px(820)`, `propagate_natural_height`; CSS `max-height` в GTK нет. Скролл панели прозрачен (`popover.volna-view-popover > contents > scrolledwindow`): панель — не листинг, её скролл не должен перекрашиваться цветом холста (issue #3).
- **Контролы** — нативные `Gtk.CheckButton` (радио в группе через `set_group`, чекбоксы) и `Gtk.ToggleButton` (сегмент): фокус, клавиатура и роли — от toolkit. Радио-строка — 26 px с текстом body (14 px), бокс 14 px, сегмент — контейнер `#1e1f22` + активная кнопка `#393b40`. Метрики строки заданы в em от **собственного** кегля строки, поэтому кегль строки — body, а не уменьшенный: `em` в длине считается от своего `font-size`, и вместе с подписью сжималась вся строка (было 16 px вместо 26 px — исправлено 2026-11-20, регрессионный тест `test_a_radio_row_is_the_design_row_height`).
- **Закрытие окна**: поповер опускается (`popdown`) до уничтожения окна — иначе GTK пишет criticals в stderr.
- **Композиция**: панель строит секции из `SETTING_FEATURES` (группировка по `section`), каждая строка — отдельный модуль настройки; панель знает только контракт `SettingFeature`, а не поля `ViewSettings`. Отключение настройки в сборке — `available(capabilities)` (пример: плотность), а не флаг в панели.
- **CSS-контракт для тестов**: `volna-view-trigger`, `volna-view-popover`, `volna-view-section`, `volna-view-section-title`, `volna-radio`, `volna-check`, `volna-seg`, `volna-seg-btn`, `volna-view-footer`; плотность — `volna-density-compact` на окне.

## 7. Тесты

Принцип [AGENTS §5](../AGENTS.md): системные тесты независимы от реализации (клики по видимым контролам + чтение отрисованных подписей/классов), остальное — по необходимости. `gtk_display` (приватный Xvfb) выносится из `tests/test_window.py` в `tests/conftest.py` — рефактор без изменения поведения.

### 7.1 Без дисплея

- `test_view_settings.py`: дефолты; `from_mapping` игнорирует мусор/неизвестные ключи; clamp zoom; неизвестные enum → дефолт; `normalized()`/`merged()` приводят режим к возможностям; frozen/value-равенство; round-trip mapping.
- `test_view_store.py`: round-trip активного вида; битый JSON и не-UTF-8 → дефолты, файл сохранён/переименован в `*.invalid-*` только при следующей записи; битое поле → дефолт; будущая схема — read-only (файл не перезаписывается); атомарная запись без tmp; идемпотентность; read-only каталог → `False`; XDG/HOME-резолвинг; нет HOME/XDG → memory-store.
- `test_core_visibility.py`: фильтрация скрытых, счётчики по видимым, `set_order`/`set_folders_first`/`set_show_hidden` с guard'ами и событиями, направления сортировки, `generation` не меняется, ingest/скан между переключениями; `test_core_order.py` — «папки первыми» и смешанный порядок при `folders_first=False`.
- тест на импорты: `display` не тянет GTK/`views`/`view_panel`;

### 7.2 Xvfb (виджеты)

- триггер ровно один, слева от пути; открывает/закрывает поповер; Esc/клик вне; `active`-состояние.
- порядок секций V1: «Сортировка» → «Параметры» → footer; секций «Пресеты»/«Группировка»/«Режим»/«Масштаб» нет.
- сортировка: выбор ключа/направления и «папки перед файлами» меняют порядок видимых подписей **только активной вкладки**; **не** запускают скан (`generation`/`ScanState` не меняются).
- две вкладки: изменили в первой — вторая сохранила свой порядок; переключение показывает разные порядки; новая вкладка наследует снимок активной.
- скрытые: dotfile появляется/исчезает только в активной вкладке; счётчики — по видимым.
- плотность: класс `volna-density-compact` появляется/снимается на окне и отражает активную вкладку.
- доступность: радио/чекбоксы — нативные `CheckButton` (checked-состояние, фокус), `Tab`/`Shift+Tab`; фокус видим.
- геометрия: `size_request` = `px(320)`, `offset.y` = 4, `offset.x` = `(request − trigger_w)//2` (в быстрых тестах); фактическая ширина контента 400 px, зазор 4 px и выравнивание по левому краю измерены пиксельным пробником на реальном окне (Xvfb). Поверхность поповера шире контента из-за прозрачных полей тени — её не ассертим.
- декомпозиция: реестр состоит из разных классов/модулей с уникальными id; панель собирается из **инжектированного** реестра (подменный `FakeSetting` в тесте появляется в UI без правок панели); все диффы фич — только поля `ViewSettings`.
- CSS-контракт: `volna-view-trigger`, `volna-view-popover`, `volna-view-section`, `volna-view-section-title`, `volna-radio`, `volna-check`, `volna-seg`, `volna-seg-btn`, `volna-view-footer`.

### 7.3 Системные (независимы от реализации)

- сортировка меняет видимый порядок реальных файлов; выключение «Папки перед файлами» смешивает папку и файл в порядке имени;
- настройки не текут в другую вкладку;
- последний вид переживает перезапуск: изменить сортировку/скрытые, закрыть окно, создать новое окно с тем же временным `XDG_CONFIG_HOME` — вид восстановлен;
- битый конфиг не мешает старту и листингу;
- read-only конфиг: вид работает в сессии, приложение закрывается без ошибок.

### 7.4 Нефункциональные (`@pytest.mark.slow`)

- переключение скрытых/сортировки на 100k записей не блокирует UI дольше ~100–200 мс (замер до/после);
- `save()` того же документа не создаёт лишних записей (идемпотентность).

## 8. Риски и митигации

| Риск | Последствие | Митигация |
|---|---|---|
| чтение конфига на старте | падение/зависание запуска | guard'ы, memory-fallback, тест «битый конфиг не мешает старту» |
| потеря последнего вида при аварии | неожиданный вид после рестарта | запись при каждом закрытии, идемпотентность; принято как ограничение |
| dotfiles впервые скрыты | пользователь не находит файл | релиз-нота, чекбокс «Показывать скрытые файлы», тест |
| расхождение состояний вкладок | путаница «почему сортировка другая» | единственный writer — вкладка; панель всегда синхронизируется с активной; тест на изоляцию |
| дублирование логики применения | модель и вид расходятся | один метод `update_view_settings`, guard на равенство |
| регрессия тулбара | дубль/сдвиг «Вид» | тест «ровно один `volna-view-trigger`, слева от пути» |
| два окна | last-writer-wins | принято для V1; при необходимости — store в приложении и совместное состояние |
| отсутствие темы в тестах | визуальные регрессии не ловятся | визуальная сверка с макетом в запущенном приложении |
| декомпозиция настроек | больше модулей/бoйлерплейта на настройку | модуль ~40 строк + строка реестра; панель и окно не меняются; контракт покрыт тестами |

## 9. Критерии приёмки V1

- [ ] триггер «Вид» на месте, не смещается при длине пути, открывает/закрывает поповер мышью и клавиатурой;
- [ ] в поповере ровно действующие контролы: ключ/направление сортировки, скрытые, плотность; мёртвых секций нет;
- [ ] изменения применяются сразу к активной вкладке, поповер не закрывается, скан не запускается;
- [ ] вторая вкладка сохраняет свои настройки; новая вкладка наследует вид активной;
- [ ] последний вид активной вкладки переживает перезапуск; битый/read-only конфиг не мешает работе;
- [ ] dotfiles скрыты по умолчанию и включаются чекбоксом;
- [ ] радио/чекбоксы доступны с клавиатуры, фокус видим;
- [ ] визуальная сверка с макетом в запущенном приложении (`uv run volna`);
- [ ] 91 существующий тест + новые тесты зелёные, `ruff` чистый.

## 10. Отложено (проект на будущее)

### 10.1 Пресеты — реализовано (2026-11-20)

Пресет = именованный снапшот 8 полей `ViewSettings`; встроенные (`default`, `dense-list`, `large-icons`, `no-grouping`) — данные в коде (`display/presets.py`), идентичность по стабильному id. Применение записывает снапшот в **активную вкладку** (пресет — глобальный шаблон, не состояние), а `settings.json` по-прежнему хранит только последний вид.

Решения этой итерации (уточнения к §18 [05-interactions](spec/05-interactions.md) и §2 [04-components](spec/04-components.md)):

- **Хранение — отдельный `presets.json`** (схема 1: `{schema_version, presets: [{id, name, settings}]}`) в том же каталоге, что и `settings.json`. Причины: пресеты не должны теряться при сбросе последнего вида и наоборот; отдельный файл дешевле мигрировать, чем общий документ. Атомарная запись та же (`display/files.py`: `mkstemp` + `fsync` + `os.replace`; битый файл сохраняется как `presets.json.invalid-<ts>`). Более новая схема — файл read-only, приложение стартует на встроенных пресетах.
- **Правила имён** живут в модели (`PresetBook`), а не в виджетах: trim, пустое имя отклоняется, длина ≤ 64, совпадение по имени case-insensitive. Сохранение с именем встроенного пресета создаёт пользовательский оверрайд (встроенный не мутируется) и занимает его место в списке; удаление оверрайда возвращает встроенный. Переименование меняет только имя; id и снапшот сохраняются.
- **«Настроено вручную» — производное состояние.** Подпись поля = имя пресета, чьему нормализованному снапшоту равен текущий вид, иначе «Настроено вручную». `selected_preset_id` — отдельное состояние (нужно, чтобы «удалить текущий» знал, что применять дальше): ручное изменение, разошедшееся со снапшотом, снимает выбор. Ручное изменение, которое снова совпало со снапшотом, снова называет пресет.
- **Список — выпадающее меню поля, а не инлайн-список** (отклонение от макета, решение владельца 2026-11-20): поле — `Gtk.MenuButton`, список открывается меню под ним. Инлайн-список раздувал панель до 786 px и всё равно упирался в потолок 174 px, обрезая последнюю строку пополам; меню — отдельная поверхность, поэтому оно не обрезается панелью и панель не растёт с числом пресетов (замерено: 602 px и с открытым меню, и без; 12 пресетов = 360 px списка). Меню — вложенный поповер внутри поповера «Вид»: проверено, что панель при этом остаётся на экране, строки получают клавиатурный фокус, а стрелки/`Home`/`End` и `Esc` работают от `ListBox`/`Gtk.Popover`.
- **Действия живут в строке меню** (галочка, имя, карандаш, корзина) — как в макете; `SelectionMode.NONE`, потому что текущий пресет помечает галочка, а не системное выделение. Проверено настоящим X11-кликом: кнопка внутри строки забирает нажатие — действие срабатывает, строка не активируется, пресет не применяется, меню остаётся открытым. Ширина меню привязана к полю (18.8571em: `px(320)` минус отступы панели, зазор и кнопка сохранения).
- **Подпись поля при совпадении снимков**: приоритет у выбранного пресета, иначе у первого подходящего — иначе копия встроенного пресета «переименовывала» бы себя во встроенный.
- **UI:** секция «Пресеты» — первая в поповере (по макету); поле выбора с подписью и кнопка сохранения; меню с галочкой у текущего и действиями «переименовать»/«удалить» у пользовательских; диалоги «Сохранить пресет», «Переименовать пресет» и «Удалить пресет?» — каждое **своё маленькое модальное окно** (см. следующий пункт), закрываются по Esc, «Отмене» и кнопке подтверждения, фокус в подтверждении удаления — на «Отмене».
- **Переименование — диалог, а не правка строки** (отклонение от [05 §18.6](spec/05-interactions.md)): инлайн-редактор пересобирал строки списка целиком, и на длинном списке он каждый раз прыгал в начало — переименование выходило неудобным. Диалог показывает текущее имя, подтверждение неактивно для пустого и для неизменённого имени, а отказ («Пресет с таким именем уже существует») остаётся в диалоге и не теряет введённый текст. После диалога поповер и раскрытый список возвращаются, позиция прокрутки списка сохраняется при пересборке строк.
- **Диалог — отдельное модальное окно, а не оверлей главного** (отклонение от макета, где это оверлей с затемнением). Причина замерена: оверлей на всё окно заставляет GTK пересобирать снимок всего главного окна на каждое открытие и закрытие, и на большом окне (1800×1125 и больше) панель «Вид» возвращается заметно позже. Маленькое окно перерисовывает только свою карточку. Обратная сторона: затемнения фона нет, клик мимо карточки диалог не закрывает — закрывают Esc, «Отмена» и кнопки (модальность блокирует главное окно).
- **Поповер закрывается на время диалога** и открывается снова после него: у поповера свой grab, который иначе не даёт диалогу и его полю клавиатурный фокус (проверено: `entry.has_focus()` — `False` при открытом поповере). Панель возвращается **до** того, как окно диалога скрывается, поэтому паузы «панели нет» не возникает; раскрытый список и позиция прокрутки в нём восстанавливаются.
- **Осознанное отклонение от макета:** действия строки (карандаш/корзина) видны всегда, а не только на hover/`:focus-within`. В макете они скрыты через `pointer-events:none`; в GTK такого свойства нет, и сокрытие через `opacity` оставило бы невидимую кликабельную «корзину» — цена ошибки выше выигрыша в строгости вида.
- **Осознанное отклонение:** `localStorage['volna.presets.v1']` из спеки не используется — это веб-механика; в GTK-приложении единственное хранилище — файл конфигурации (см. первый пункт).

Проверено: 79 новых тестов (40 модель/хранилище, 39 оконных системных), полный набор — 427 passed, `ruff` чистый; приложение запущено, панель и оба диалога сверены скриншотами с макетом.

## Приложение C. Безопасность (OWASP-самопроверка)

Изменения проверены по релевантным читшитам OWASP (это внутренняя проверка, не сертификация):

- **Input validation / JSON**: конфиг читается только как JSON и валидируется по полям (`from_mapping` не бросает, неизвестное → дефолт, zoom clamp); никакого `eval`/`pickle`/исполнения кода из конфига; неверная схема не перезаписывается.
- **Filesystem**: путь из `XDG_CONFIG_HOME`/`HOME`, файл создаётся `mkstemp` (0600), каталог 0700, запись атомарная через `os.replace` (симлинк заменяется, а не его цель); битый файл сохраняется как `*.invalid-*`, а не затирается.
- **Отказоустойчивость**: любые `OSError`/`UnicodeDecodeError`/`ValueError` при чтении — `WARNING` и дефолты, старт не падает; запись при закрытии не мешает штатному выходу.
- **Данные**: хранятся только настройки отображения (режим/сортировка/скрытые/плотность/служебные поля), никаких путей, имён файлов, секретов или телеметрии; сетевого кода нет.
- **Остаточный риск**: конфиг — данные пользователя; при его подмене можно изменить только вид листинга (не пути и не операции). Огромный/враждебный JSON ограничен парсером стандартной библиотеки; отдельного лимита размера нет — для V1 приемлемо (файл создаёт само приложение).

Проверка итерации пресетов (2026-11-20, по тем же читшитам: Input Validation, File Upload/Path Traversal-смежное «файл как данные», Error Handling):

- **Имена пресетов** — данные пользователя, попадающие только в список и в файл: `clean_name` обрезает пробелы и до 64 символов, пустое имя отклоняется, сравнение регистронезависимое; в JSON идут как строка `json.dumps` (экранирование — библиотека), в UI — через `Gtk.Label`, разметки нет, инъекции нет.
- **Чтение `presets.json`**: только `json.loads`; запись валидируется по полям (тип, префикс id `custom-`, наличие `settings`-объекта). Невалидные записи **пропускаются по одной** с `WARNING` и заметкой в статусе, а не роняют загрузку; дубли id/имён отбрасываются.
- **Пути**: имя файла — константа в каталоге из `XDG_CONFIG_HOME`/`HOME`, никаких имён из данных в пути; каталог 0700, временный файл через `mkstemp` (0600), замена `os.replace` (симлинк заменяется, а не его цель).
- **Устойчивость**: битый/не-UTF-8 файл сохраняется как `presets.json.invalid-<ts>` перед следующей записью; более новая схема делает файл read-only (никогда не затирается); неудачная запись не скрывается — статус говорит «не сохранено: изменения только в памяти», а пресет остаётся доступен до конца сессии.
- **Данные**: в файл попадает только снапшот отображения (8 полей) и имя; ни путей, ни содержимого каталогов, ни телеметрии.
- **Отмена/ошибка**: удаление подтверждается модальным диалогом с фокусом на «Отмене», Esc и «Отмена» закрывают без изменений; встроенные пресеты удалить и переименовать нельзя (проверяется в модели, а не только скрытием кнопок).
